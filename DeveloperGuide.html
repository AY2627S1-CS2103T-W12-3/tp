Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

UI component

The API of this component is specified in Ui.java.

The first diagram shows the parts created or used by MainWindow, including CommandBox, ResultDisplay, PersonListPanel, EventListPanel, ReminderPanel, StatusBarFooter, and TutorialWindow. MainWindow also uses TagListViewModel to keep the Tags view synchronized with contact and tag data.

The inheritance diagram shows all ten subclasses of the abstract UiPart, which captures behavior shared by visible GUI parts. Each UiPart box represents the same superclass, repeated to keep the arrows clear. TagListViewModel and WindowBounds are helpers rather than UiPart subclasses.

The HelpWindow provides an in-app command quick reference. Its read-only, scrollable command table is populated by HelpWindow using the command words defined by the corresponding command classes, while its FXML file controls the resizable layout. The User Guide URL remains available for more detailed instructions. The window's Close button is marked as the JavaFX cancel button, allowing users to dismiss it by selecting the button or pressing Esc without exiting the application. MainWindow hosts the guided TutorialWindow as an overlay above the main application scene. The sixteen-step tour highlights the Contacts, Events, and Tags views, contact commands and input, lists, details, the event member list, and Help. It also introduces keyboard navigation. It selects an existing contact, event, or tag when needed, without changing saved data; empty lists show their existing hints. The event details pane scrolls to the member list for its step, and highlights inside a scroll pane are clipped to the visible viewport. The dim backdrop leaves the highlighted area clear while a transparent blocker and disabled command box prevent commands from running during the tour. UiManager opens the overlay on first launch. MainWindow records the tutorial preference when the user closes or finishes it. The tutorial command, the Tutorial item beside Help in the top bar, and the F2 shortcut can open the overlay again at any time. TutorialCommand returns a CommandResult whose shouldShowTutorial() flag asks MainWindow to open the overlay, in the same way that shouldShowHelp() opens the Help window. The overlay handles Left and Right Arrow navigation, Escape dismissal, and Tab focus movement before key events can reach the command box or the main window's navigation shortcuts. Tab and Shift+Tab cycle through the card's enabled buttons so that keyboard focus cannot leave the card.

CommandBox keeps submitted, nonblank commands in a session-only list. The list has no configured cap or eviction; its practical limit is the JVM heap, and it is discarded when the app closes. It records an attempt before execution so commands that fail validation can be recalled for correction. Up and Down move through the list, with the current input saved as a draft and restored after the newest entry. Browsing does not execute a command or modify stored entries. While Logic awaits delete confirmation, arrow-key navigation is paused and the response is not added to history. Inserting a command from the sidebar resets history navigation.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

At launch, MainWindow obtains the saved size, position, and maximized state from GuiSettings. It selects the screen containing the saved position, or the primary screen if that display is no longer connected. WindowBounds then clamps the saved dimensions and coordinates to the screen's visual bounds, which exclude operating-system areas such as the taskbar or dock. The preferred minimum size is also capped to the available area, so it cannot force the window beyond a smaller display. MainWindow tracks the latest non-maximized bounds separately, allowing a maximized window to be restored without replacing its normal dimensions. If a maximized window is moved to another monitor before closing, the normal bounds retain their size and relative position on that monitor so the next launch maximizes there. Screen fallback is logged at WARNING, bounds adjustments at INFO, and maximized-state restoration and saving at FINE.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data. The Contacts view displays the filtered contact list beside a details pane, follows a selected contact by permanent member ID across edits and reordering, and clears the selection when that ID leaves the displayed list. Contact cards, contact details, event rosters, and tag member lists display ID: <number> from the saved contact, independently of the current contact filter. The details pane displays all saved contact fields, showing a placeholder for unset optional fields and no tag chips for an empty tag set. It also derives assigned-event rows from the live event list. The Events view resolves each assigned member to contact role, organisation, and tags, and refreshes when contact data changes. Contact and event views keep their details pane above a minimum width, then stack the list above details when the window is narrow. Sidebar command rows insert only the command word into the command box and show its format and an example; rows also support keyboard activation. Selecting a tag shows all saved contacts assigned to it, independent of the current contact filter, and refreshes names, roles, organisations, and tags when contact data changes. A window-level key filter owns Navigation-mode input: J and K move within the active view, S cycles views, and I returns to Command mode. Other unmodified keys are consumed before focused controls can act on them. Entering Navigation mode transfers focus to the mode indicator, preventing controls such as reminder dismissal buttons from retaining keyboard activation.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands. Commands such as members and the tag commands can return a view selection request that MainWindow applies through the same view controls used by the sidebar.
  • depends on some classes in the Model component because it displays Person objects from the model.

API : Logic.java

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a CoordiMateParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand). For delete, LogicManager first calls resolvePerson and returns a confirmation prompt without executing the deletion.
  3. If the next input is y or Y, LogicManager creates a command for the resolved Person and executes it on a candidate model. That command deletes the contact from the candidate, which is saved before the live model changes. Any other input cancels the deletion.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the CoordiMateParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The CoordiMateParser returns that object as a Command object.

Command error messages follow these conventions:

  • Use sentence case and full stops for explanations, without an Error! prefix or exclamation marks.
  • For malformed command syntax, use ParserUtil.createInvalidFormatException(Command.MESSAGE_USAGE). Usage text has a command description, Parameters:, and Example: on separate lines.
  • Every command error includes the relevant command's usage once. CoordiMateParser appends it to parse errors; LogicManager appends it to execution and storage errors. Messages.withUsage avoids duplicating usage.
  • For unknown or repeated parameters, name the offending prefix: Unknown parameter: x/. or Parameter evn/ may only be specified once.
  • For invalid field values, explain the constraint and provide an Example: using the failing parameter's prefix.
  • Distinguish missing parameters, which show command-format guidance, from supplied but empty values, which use <Field> must not be empty. Example: <prefix><value>. Optional contact fields can still be cleared intentionally.
  • Storage-loading errors use Saved data could not be loaded. Check the local data file. for every data type.
  • For execution errors, explain what failed and how to correct it. Reuse the templates in Messages for missing contacts, events, and tags, and for unmatched or ambiguous contact identifiers.
  • Add No changes were made. when an attempted change is rejected without modifying the saved data.

Model component

API : Model.java

The Model component,

  • stores CoordiMate data, including all Person objects (which are contained in a UniquePersonList object).
  • assigns each saved Person an immutable MemberId. CoordiMate maintains the next ID to allocate, and UniquePersonList rejects duplicate IDs. Replacing or editing a contact preserves its ID.
  • stores a case-insensitively unique global tag list. Every tag assigned to a contact is also registered in this list; adding, editing, or replacing contacts registers any missing tags while preserving existing unused tags.
  • stores all Event objects. Each Event records its assigned members as an ordered list of contact Names. CoordiMate keeps these lists in sync with the contacts: deleting a contact removes their name from every event, and renaming a contact updates it.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • keeps an archive view, which decides whether the filtered contact list and the filtered event list show active or archived items.
  • stores a UserPrefs object that represents the user’s preferences, including window size and position, maximized state, and whether the first-launch tutorial has been completed or dismissed. This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: CoordiMate already keeps a global UniqueTagList, but each Person holds its own Tag objects, which are compared with those in the list by value and are not necessarily the same objects. The alternative, arguably more object-oriented, design below has each Person reference the Tag objects in that list instead, so CoordiMate maintains exactly one Tag object per unique tag.

Storage component

API : Storage.java

The Storage component,

  • can save both CoordiMate data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonCoordiMateStorage and JsonUserPrefsStorage (one class per data file).
  • converts CoordiMate data through JsonSerializableCoordiMate, which stores contacts (JsonAdaptedPerson), events (JsonAdaptedEvent), and the global tag list (JsonAdaptedTag) as separate lists. Each contact also stores its own tags, and each event records its members by contact name rather than by member ID.
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

The tutorial flag is saved with the other user preferences. Preference files without that field are read with the tutorial flag set to false, so the tutorial is offered until the user closes or finishes it.

Previously saved digit-only phone numbers with at least three digits remain valid model data, so older JSON files can still load. The command parser applies the current 7–15-digit rule whenever a user supplies a phone number for add or edit; editing another field does not require replacing a legacy phone number.

When loading JSON data, explicitly saved tags are validated and restored before contacts. If a contact uses a tag that is missing from the saved global tag list, CoordiMate registers it automatically. This also migrates older files without an explicit tag list: default tags are retained and tags used by contacts are added. Existing saved tag order, capitalization, and unused tags are preserved.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Permanent member IDs

Each saved contact has a unique MemberId in the range 1 to 2147483647. The displayed label is ID: <number>; search results, filters, and list order never determine its value.

Allocation and editing

Person holds an immutable ID. A new contact can be an unassigned draft until CoordiMate#addPerson accepts it. CoordiMate allocates from its long nextMemberId counter, advances the counter after successful additions, and preserves imported IDs. UniquePersonList rejects duplicate assigned IDs and prevents replacements from changing a contact's ID. Bulk replacement reserves all supplied IDs before assigning any missing ones. Copies and resets preserve both IDs and allocation state, including when the highest ID has been deleted. Deleting contacts does not recycle IDs. clear creates a new empty dataset and resets allocation to 1. The counter value 2147483648 represents exhaustion; further automatic allocation is rejected. AddCommand translates the allocation failure into a CommandException with the message No more member IDs are available. so the UI displays normal command feedback. Contacts, tags, the allocation counter, and the saved file remain unchanged.

Command targeting

ParserUtil#parseMemberId parses a positive integer without converting it to a list position. MemberIdResolver searches Model#getCoordiMate().getPersonList(), including contacts hidden by the active view. edit and delete resolve one ID; assign and unassign resolve every ID before changing an event. An unknown ID reports No contact exists with member ID: <number>. Use an existing member ID. without changing data or falling back to a position. Event membership and attendance still use contact names internally; the commands translate IDs to those names after resolution.

Deletion confirmation retains the resolved contact. On confirmation, the command resolves its ID again and rejects the deletion if that contact was removed or edited. Reordering or filtering cannot redirect it.

Storage and migration

JsonAdaptedPerson writes a numeric memberId, and JsonSerializableCoordiMate writes a numeric nextMemberId. Loading first parses all contacts and finds the highest supplied ID. It then validates the saved counter, or derives one greater than the highest ID when no counter exists. Contacts with missing or null IDs receive consecutive IDs in file order starting from that counter. An entirely legacy file therefore receives IDs starting at 1; mixed files preserve all existing IDs before allocating new ones.

Loading does not rewrite the file. The next successful save records migrated IDs and the counter, so future launches retain IDs and do not reuse deleted ones. Duplicate IDs, non-integral or out-of-range values, a counter not greater than every saved ID, and exhausted allocation for a contact without an ID reject the file through the normal storage-loading error path. Numeric strings are not accepted as IDs or counters.

Design considerations and verification

A saved counter avoids reusing an ID after deleting the highest-numbered contact. Deriving the next ID from the current list on every launch would lose that history. Full-list lookup keeps command behavior independent of the UI and is adequate for the expected contact count.

MemberIdPersistenceTest covers saved counters, legacy and mixed-file migration, invalid data, and exhaustion. PermanentMemberIdCommandsTest covers targeting across searches, tag filters, event-member views, empty results, reordering, and restarts. It also runs a legacy migration through editing, event assignment and unassignment, deletion, saving, and restart, then checks that a deleted ID cannot target another contact. UI tests verify the same labels and selection behavior in Contacts, Events, and Tags.

Saving data atomically

Commands that edit contacts, event details, tags, or attendance either take effect in full, both in the app and in the data file, or not at all. This keeps the displayed data and the saved data identical even when the data file cannot be read or written, and meets the requirement that saved data is not lost if the app terminates unexpectedly. Reminder dismissal uses a separate save path with a session-only fallback, described in Dismissing reminders.

Implementation

Two mechanisms work together.

1. Commands run on a copy of the model. LogicManager#execute passes commands that edit contacts, event details, tags, or attendance to LogicManager#executeAtomicCommand. These are AddCommand, EditCommand, DeleteCommand, ClearCommand, AddEventCommand, EditEventCommand, DeleteEventCommand, AssignCommand, UnassignCommand, MarkAttendanceCommand, and the tag commands that extend MutatingTagCommand.

executeAtomicCommand does the following:

  1. It calls Storage#readCoordiMate() to check that the existing data file can still be loaded. If it cannot, the command is rejected with a load error and the file is left untouched, so that the user can repair it. A missing data file is not an error.
  2. It creates a second ModelManager, the candidate, from a copy of the live model's data, including member IDs and allocation state. Its filtered contact list initially shows the same contacts as the live view. Commands resolve member IDs against the complete saved contact list in either model.
  3. It executes the command on the candidate. If the command fails, the candidate is discarded.
  4. It saves the candidate's data with Storage#saveCoordiMateIfUnchanged. This compares the file with the revision loaded at startup or last saved by this window while holding a lock shared by CoordiMate instances. If another window changed the file, the command is rejected and the candidate is discarded. Other save failures still report an error such as Event could not be saved. No changes were made.
  5. Only then does it call Model#setCoordiMate to replace the live model's data with the candidate's data, which updates the UI.

The live model is not touched until step 5, so a failure at any earlier step leaves the app exactly as it was.

After committing, LogicManager adjusts the displayed contact list where needed: add and edit show all contacts again so that the changed contact is visible, and renaming an event whose members are being shown keeps that view on the renamed event (see Keeping events in sync with contacts).

2. The data file is replaced in one step. JsonCoordiMateStorage#saveCoordiMate writes the new data to a temporary file named coordimate-*.tmp in the same folder as the data file, then moves it over the data file using StandardCopyOption.ATOMIC_MOVE. The data file therefore always holds either the complete old data or the complete new data. The temporary file is deleted if anything fails.

Deleting a contact adds a confirmation step. For a delete command, LogicManager checks that the data file can be loaded, resolves the contact, stores it in its pendingDelete field, and returns a confirmation prompt. The next input is treated as the answer, not as a command: y or Y runs the deletion through executeAtomicCommand, and any other input cancels it.

Commands that do not change data, such as list, search, filter, members, and listtags, are executed directly on the live model without saving. They cannot overwrite a newer or invalid data file. A window that has become stale can still show its loaded data, but its next save is rejected until it is reopened. Reminder dismissal uses the same conditional save and retains its session-only fallback when saving fails.

CommandResult.View carries one requested view, or NONE when a command does not request a view change. MainWindow applies a requested view through the same view controls used by the sidebar.

Commands that produce contact, event, or tag results request the corresponding CommandResult.View, which MainWindow applies after successful execution. A failed command does not return a view request, so the current tab remains selected. Contact deletion requests Contacts when its confirmation prompt is displayed. assign and unassign deliberately return View.NONE; the current tab remains selected while its observable contact or event details refresh.

Design considerations

Aspect: How a command is prevented from taking effect when saving fails

  • Alternative 1 (current choice): Execute the command on a copy of the model, save the copy, then replace the live model's data.

    • Pros: Works for the editing commands listed above without command-specific rollback code. The UI never shows an edit that was not saved.
    • Cons: Copies all data for each command, which is acceptable for the expected 250 contacts. Each new command using this save path must be added to the list in LogicManager#execute.

  • Alternative 2: Execute the command on the live model, and restore a snapshot if saving fails.

    • Pros: No copy is needed when saving succeeds.
    • Cons: The UI observes the model, so it briefly shows a change that is then reverted.

  • Alternative 3: Have each command undo its own change if saving fails.

    • Pros: Uses the least memory.
    • Cons: Every command needs correct undo logic, which is easy to get wrong.

Dismissing reminders

LogicManager creates a shared ReminderService and supplies it to CoordiMateParser, which passes it to DismissCommandParser and DismissCommand. The CLI command and the panel's Dismiss button therefore use the same dismissal history and storage behavior.

  1. DismissCommandParser uses ParserUtil#parseIndex to accept one positive, 1-based index. Missing input produces a format error; invalid integers and extra arguments are rejected before execution.
  2. DismissCommand#execute obtains the refreshed reminder list from ReminderService#getReminders and checks the index against its size. UpcomingEventFinder orders this list by start time and then by event name, ignoring case; date-only starts count as midnight for sorting. ReminderPanel renders the same list with 1-based indexes and regenerates the rows whenever it changes. An out-of-range index, including an empty list, produces a command error without reading or writing storage.
  3. The command passes the selected Event to ReminderService#dismissReminder. The service creates a copy with updated dismissal history, checks that the existing data can be loaded, and saves the candidate before updating the live event. Event details, members, attendance, and the contact filter are preserved.
  4. On success, the command returns Reminder dismissed: EVENT_NAME. without requesting a view change. If reading or saving fails, the service keeps the dismissal in its session map, refreshes the list, and throws ReminderDismissalException. The command logs the failure and returns CommandResult.warning. MainWindow checks CommandResult#isWarning and uses ResultDisplay#setWarningFeedback to show the existing Not saved status. The persisted history is unchanged, so the reminder may return after restart.

LogicManager returns the dismissal result directly, bypassing both executeAtomicCommand and the generic post-command save. ReminderService already performs the save; a second save would be redundant and could replace the warning with an unrelated error. The normal final reminder refresh still runs after execution.

ReminderLogicIntegrationTest covers ordering, edits, persistence, event data, and read/write failures using a controlled clock and temporary JSON files. MainWindowReminderTest covers immediate panel updates, renumbering, feedback, selected tabs, and command focus.

Event attendance

Attendance records whether each member of an event was present or absent.

Implementation

An Event is immutable. It stores:

  • its members as a List<Name> of contact names, in the order they were assigned.
  • its attendance as a Map<Name, AttendanceStatus>, where AttendanceStatus is an enumeration of PRESENT and ABSENT. A member with no entry in the map has not been marked.

The Event constructor rejects an attendance record that contains a name which is not a member, so attendance can never exist for someone who is not assigned to the event.

The markattendance command works as follows:

  1. MarkAttendanceCommandParser checks that evn/, mem/, and att/ each appear exactly once, converts the status with AttendanceStatus#fromString, and validates the member name with ParserUtil#parseName.
  2. MarkAttendanceCommand#execute finds the event and then the member, both ignoring case. It uses the member's name as stored in the event, so that feedback and the attendance record use the saved capitalisation.
  3. If the member already has the requested status, the command reports that no changes were made.
  4. Otherwise it calls Event#withAttendance, which returns a copy of the event with the member's status set, and replaces the event with Model#setEvent.

The command changes data, so it runs through executeAtomicCommand as described above.

Other commands keep the attendance record consistent with the members:

Change Effect on attendance
assign adds members Existing attendance is kept. New members are not marked.
unassign removes members The removed members' attendance is removed.
editevent renames or reschedules the event Attendance is kept.
edit renames a contact The contact's attendance moves to the new name in every event.
delete deletes a contact The contact's attendance is removed from every event.

In the data file, JsonAdaptedEvent stores attendance as an attendance object that maps each member's name to "present" or "absent". A file with no attendance field loads with no attendance recorded, so files saved by earlier versions still load. A file is rejected as invalid if a status is neither value or if a name in attendance is not in the event's members.

EventListPanel shows Present, Absent, or Not marked beside each member of the selected event, and the number of members with each status.

Design considerations

Aspect: Where attendance is stored

  • Alternative 1 (current choice): Each Event stores a map from member name to status.

    • Pros: An event and its attendance are saved, copied, and replaced as one unit, so they cannot disagree. Removing a member and their attendance is a single change.
    • Cons: A contact's attendance across events can only be found by looking through every event.

  • Alternative 2: Store attendance records in a separate list, each referring to an event and a contact.

    • Pros: Makes it easy to query one contact's attendance across all events.
    • Cons: Every change to an event or contact must also update the separate list, or records are left behind.

Aspect: How "not marked" is represented

  • Alternative 1 (current choice): A member with no entry in the map is not marked.

    • Pros: Newly assigned members need no extra data, and older data files load without conversion.
    • Cons: Code that counts statuses must derive the not-marked count from the members.

  • Alternative 2: Add a third NOT_MARKED status and give every member an entry.

    • Pros: Every member has an explicit status.
    • Cons: Every command that adds a member must also add an entry, and older data files would need converting.

Filtering contacts

The filter command lists the contacts that match every given FIELD/VALUE pair, where the field is tag, event, or organisation.

Implementation

Filtering is split into parsing, which does not need saved data, and resolving, which does.

Parsing. FilterCommandParser turns the arguments into a list of FilterCriterion records, each holding a FilterField and the value as typed.

  1. It finds every FIELD/ token, which is a run of letters followed by / at the start of the arguments or after a space. A token is ignored if an odd number of quotation marks comes before it, since it is then inside a quoted value.
  2. The value of each field is the text up to the next token. Surrounding quotation marks are removed.
  3. The field name is matched to a FilterField, ignoring case.

An unclosed quotation mark is rejected only when a FIELD/ token follows it, because it is then unclear where the value ends. With no token after it, the quotation mark is kept as part of the value, since saved names may contain one. For example, filter event/"Cali matches an event named "Cali.

Resolving. FilterCommand#execute turns each criterion into a Predicate<Person> using the model:

Field The value must match, ignoring case A contact matches if
tag a tag in Model#getTagList() it has that tag
event the name of a saved event it is a member of that event
organisation the organisation of at least one saved contact its organisation is that value

If a value matches nothing, the command throws a CommandException with No matching value found. before the displayed list is changed. This tells the user about a mistyped value instead of showing an empty list. Otherwise the predicates are combined with Predicate#and and passed to Model#updateFilteredPersonList.

filter does not change data, so it is executed directly on the live model.

Note: The event predicate holds the Event found when the command was executed. Since an Event is immutable, the filtered list does not follow later changes to that event's members until filter is run again. The members command differs: it uses EventMembersPredicate, which looks the event up each time it is tested.

To add a filter field, add a constant to FilterField, add a case to FilterCommand#resolvePredicate, and update FilterCommandParser.MESSAGE_INVALID_FIELD.

The search command is implemented separately. SearchCommand uses ContactMatchesKeywordPredicate, which tests whether a contact's name, phone, email, address, or organisation contains the keyword, ignoring case. It compares substrings with String#regionMatches(true, ...), using the same case comparison as duplicate-name detection.

Design considerations

Aspect: Syntax of a filter

  • Alternative 1 (current choice): Full field names, as in filter tag/EXCO event/Final Concert.

    • Pros: The fields are self-explanatory, and a field is added by extending one enumeration.
    • Cons: Differs from the short prefixes of other commands, such as t/.

  • Alternative 2: Reuse the existing prefixes, as in filter t/EXCO evn/Final Concert.

    • Pros: Consistent with other commands.
    • Cons: Some prefixes would mean different things in different commands, and organisation would need o/, which is easy to confuse with other single-letter prefixes.

Aspect: What happens when a value does not exist

  • Alternative 1 (current choice): Reject the command with No matching value found.

    • Pros: Distinguishes a mistyped value from a valid value that no contact has.
    • Cons: The command must look the value up in the model before filtering.

  • Alternative 2: Show an empty list.

    • Pros: Simpler to implement.
    • Cons: The user cannot tell whether the value was mistyped.

Keeping events in sync with contacts

An event refers to its members by contact Name, not by Person object. Contacts are replaced with new Person objects whenever they are edited, so a name is the stable way to refer to one. In exchange, the app must keep the names in events consistent with the saved contacts.

Implementation

Renaming and deleting contacts. CoordiMate updates events whenever a contact changes:

  • CoordiMate#setPerson checks whether the contact's name has changed. If so, every event that lists the old name is replaced with a copy that lists the new name in the same position and carries the contact's attendance over.
  • CoordiMate#removePerson replaces every event that lists the contact with a copy that has neither the name nor its attendance.

Both use CoordiMate#getEventsWithReplacedMember, which builds all the updated events before anything is changed. As a safeguard, if an event already has a member with the new name, it throws MemberNameConflictException and no data is changed. EditCommand reports this as Cannot rename this contact because an event already has a member with that name. No changes were made.

Loading data. JsonSerializableCoordiMate#toModelType rejects a data file in which an event lists a member who is not a saved contact, with Event members must refer to existing contacts.

Showing an event's members. MembersCommand filters the contact list with EventMembersPredicate. The predicate holds the event's name and the model's live event list, and looks the event up each time it is tested. The displayed members therefore follow later changes:

  • After unassign, the removed member no longer matches and disappears from the list.
  • After deleteevent, no event has that name, so the list becomes empty.
  • After editevent renames the event, the old name would match nothing, so LogicManager#keepMembersViewAfterRename replaces the predicate with one for the new name.

A filtered list re-tests its predicate only when the contact list changes. For this reason CoordiMate#resetData replaces the events before the contacts: when the contacts are replaced and the predicate is tested again, it already sees the new events.

Design considerations

Aspect: How an event refers to its members

  • Alternative 1 (current choice): By contact name.

    • Pros: Readable in the data file, where members is a list of names. Names are already unique among contacts.
    • Cons: Renaming or deleting a contact must update every event, as described above.

  • Alternative 2: By a reference to the Person object.

    • Pros: No lookup is needed to get a member's details.
    • Cons: Person is immutable and is replaced on every edit, so every event would need updating on any edit, not only on a rename.

  • Alternative 3: By a generated contact ID.

    • Pros: Renaming a contact would not affect events.
    • Cons: Needs a new ID field and a change to the data file format, and makes the data file harder to edit by hand.

Marking contacts as on leave

A contact can be marked as on leave until a given date. The status ends by itself once that date has passed.

Implementation

LeaveDate holds the last day of a contact's leave, in dd-MM-yyyy format. Person stores it as an optional field, like birthday and note, and exposes:

  • Person#getLeaveDate(), which returns the saved date, even if it has passed.
  • Person#isOnLeave(LocalDate today), which returns true if a date is saved and today is not after it.

LeaveDate has two validity rules, in the same way that Phone separates saved values from newly entered ones:

  • LeaveDate#isValidLeaveDate accepts any real date, including past dates, so that leave which has ended can still be loaded from the data file.
  • LeaveDate#isValidInputLeaveDate also requires the date not to be before today. ParserUtil#parseLeaveDate applies this rule to dates entered with lv/, so new leave cannot already have ended.

The lv/ prefix is handled like the other optional contact fields:

  1. AddCommandParser sets the leave date if lv/ has a value, and leaves it unset if lv/ is empty or omitted.
  2. EditCommandParser records the new date in EditPersonDescriptor#setLeaveDate. An empty lv/ records null, which clears the leave. EditPersonDescriptor#isLeaveDateEdited distinguishes clearing from omitting.
  3. EditCommand#createEditedPerson keeps the existing leave date unless it was edited.

How leave ends. Nothing is changed when a leave date passes. Instead, the UI asks each contact whether it is on leave on the current date:

  • PersonCard shows an On leave until badge only if Person#isOnLeave(today) is true.
  • PersonListPanel shows the date in the details pane in the same case, and — (not on leave) otherwise.

PersonListPanel reads today from a Clock, which tests replace to control the date. A window left open past midnight still needs redrawing, so MainWindow's existing one-minute reminder timer also calls PersonListPanel#refreshIfDateChanged(). If the date differs from the one last shown, the panel refreshes its list cells, which rebuilds each PersonCard, and redraws the selected contact's details. Otherwise it does nothing, so the list is redrawn at most once a day.

The ended date stays in the contact and in the data file until the user replaces or clears it. Code that copies a contact, such as CoordiMate#setTag and CoordiMate#removeTag, passes the leave date on, so it is never dropped.

In the data file, JsonAdaptedPerson stores the date in a leaveUntil field. Files saved before this feature have no such field, and their contacts load as not on leave.

Assertions and logging. ParserUtil#parseLeaveDate asserts that the parsed leave covers today, which checks that the input rule was applied. AddCommand and EditCommand log at INFO level when a contact's leave is set or cleared.

Design considerations

Aspect: How leave ends once its date has passed

  • Alternative 1 (current choice): Keep the date, and check it against the current date whenever a contact is displayed.

    • Pros: No data needs changing when leave ends, so no save is needed at launch or at midnight. The behaviour is easy to test by passing a fixed date to Person#isOnLeave.
    • Cons: Ended dates remain in the data file. A window left open past midnight must be redrawn, which needs the date check described below.

  • Alternative 2: Remove ended leave dates from the data, for example at launch.

    • Pros: The data file only contains leave that is still active.
    • Cons: Requires saving at launch, which no other feature does, and still needs a check for leave that ends while the app is open.

Aspect: How an open window notices that the date has changed

  • Alternative 1 (current choice): Check the date on each tick of the existing one-minute reminder timer.

    • Pros: Adds no new timer. Still works if the computer sleeps through midnight or its clock or time zone changes, because each tick compares the current date with the date last shown.
    • Cons: The badge can stay visible for up to a minute after midnight.

  • Alternative 2: Schedule a timer for the next midnight, then reschedule it each day.

    • Pros: Updates exactly at midnight.
    • Cons: A second timer to start and stop with the window. A timer scheduled before a sleep, or a clock or time zone change, can fire at the wrong time.

Aspect: How leave is entered

  • Alternative 1 (current choice): An optional lv/ field in add and edit.

    • Pros: Consistent with the other optional contact fields, including clearing with an empty prefix.
    • Cons: Users must know that leave is set through edit.

  • Alternative 2: A separate command, such as leave MEMBER_ID until/DATE.

    • Pros: Easier to discover.
    • Cons: Duplicates the contact lookup and validation already in edit, and adds a second way to change a contact.

Archiving contacts and events

archive, unarchive, archiveevent, and unarchiveevent hide a contact or an event from the normal lists without deleting it. list archived shows only archived items, and list returns to the active ones.

Implementation

The archive flag. Person and Event each have a boolean archived field, which is part of equals and hashCode. Both are immutable, so archiving returns a copy from withArchived(boolean):

  • Event#withArchived builds the copy through the full constructor. Every other Event copy method, such as withAttendance and withDetails, passes the flag on.
  • Person takes archived as the last parameter of its full constructor, the one that also takes a member ID. Every copy of an existing contact uses that constructor, so the compiler makes each copy pass the flag on: Person#withArchived, Person#withMemberId, EditCommand#createEditedPerson, and the tag updates in CoordiMate#setTag and CoordiMate#deleteTag. The shorter constructors create new contacts, which are never archived. withMemberId matters when loading a data file saved before member IDs existed: CoordiMate#addPerson gives each contact an ID, and the contact must stay archived.

Archiving changes nothing else: an archived contact keeps its name in event member lists, and an archived event keeps its members and attendance.

Hiding archived items. ModelManager keeps the archive view, a BooleanProperty that is true while archived items are shown, separately from the contact filter set by commands:

  • The filtered contact list shows a contact only if its archived value matches the view and it matches the latest predicate passed to updateFilteredPersonList. getFilteredPersonPredicate still returns that predicate, so code such as LogicManager#keepMembersViewAfterRename sees the command's filter and not the combined test.
  • A filtered event list, Model#getFilteredEventList, shows the events whose archived value matches the view. The Events tab and its count use this list. A contact's details pane uses the full event list instead, so that archived events still appear in the contact's history.
  • Model#setShowingArchived switches both lists. MainWindow observes showingArchivedProperty to:
    • change the tab titles to Archived contacts and Archived events,
    • tell PersonListPanel and EventListPanel to show No archived contacts. or No archived events. for an empty list, and the event list heading to read Archived events, and
    • show short sidebar command lists, archivedContactsCommands and archivedEventsCommands in MainWindow.fxml, which list only the restore command and list, in place of the full lists for the Contacts and Events tabs.

Because the view is applied inside the model, search, filter, and members hide archived contacts without any change to those commands.

The sequence diagram below shows archive 12. ArchiveCommand finds the contact by its permanent member ID with MemberIdResolver, which searches all saved contacts, so the command works whatever the displayed list shows. Like edit, it is one of the commands that LogicManager executes on a copy of the model, as described in Saving data atomically. LogicManager copies the current archive view onto that copy, so that commands which read the displayed list see the same contacts on the copy as on the screen.

Effects on other features.

  • ReminderService#refreshReminders skips archived events, so archiving an event removes its reminder at once.
  • ReadOnlyCoordiMate#findEvent(String) returns the saved event with a given name, ignoring case and including archived events. ArchiveEventCommand, AddEventCommand, and EventMembersCommand use it.
  • The instance method EventMembersCommand#findEvent, used by assign and unassign, rejects an archived event. MembersCommand, MarkAttendanceCommand, EditEventCommand, and DeleteEventCommand search the full event list, so they still work on archived events.
  • AssignCommand resolves its member IDs with EventMembersCommand#resolvePersons and rejects the whole command if any of the contacts is archived. UnassignCommand does not check, so an archived contact can still be removed from an event.
  • The Tags member list in MainWindow and the event member list in EventListPanel mark archived contacts as (archived), and PersonListPanel marks archived events in a contact's event list.
  • AddEventCommand reports an archived duplicate with a hint to unarchive it, since the user cannot see the existing event.
  • ModelManager#addPerson sets the view back to active, like the filter it already clears, and LogicManager does the same on the displayed model after add and addevent, so that the new item is visible. The first is needed because AddCommand looks up the new contact in the displayed list of the model copy to select it.

Storage. JsonAdaptedEvent and JsonAdaptedPerson both read archived as a Boolean creator parameter. A missing or null value is read as false, so data files saved before archiving existed still load.

Design considerations

Aspect: How archived items are hidden

  • Alternative 1 (current choice): The model combines the archive view with every contact filter.

    • Pros: Every command that filters contacts respects the view without changes. Future filters also respect it.
    • Cons: The filtered list's predicate is no longer exactly the one a command set, so ModelManager must keep the command's predicate separately for getFilteredPersonPredicate.

  • Alternative 2: Each command adds !person.isArchived() to its own predicate.

    • Pros: The model stays unchanged.
    • Cons: Easy to forget in a new command, and list archived would have to change every command's behaviour.

Aspect: How archive and unarchive identify a contact

  • Alternative 1 (current choice): By permanent member ID, as edit, delete, and assign do.

    • Pros: Consistent with the other contact commands. A contact can be restored from any view, and a search or filter cannot change which contact an ID refers to.
    • Cons: The user needs to know the ID, which is shown on each contact card.

  • Alternative 2: By index in the displayed list.

    • Pros: Easy to use right after a search.
    • Cons: Restoring a contact would first need list archived, and indexes shift when the list changes.

Aspect: Where archived items are stored

  • Alternative 1 (current choice): In the same lists, with an archived flag.

    • Pros: Names stay unique across active and archived items, events keep referring to archived contacts by name, and unarchiving only flips the flag.
    • Cons: Every list that should hide archived items must filter them out.

  • Alternative 2: In separate archive lists.

    • Pros: The normal lists never contain archived items.
    • Cons: Duplicate checks, event member lookups, and the data file format would all have to handle two lists, and moving an item between lists could break the links between events and contacts.

Non-Functional Requirements

  1. Should work on any mainstream OS (Windows, macOS, Linux) as long as it has Java 25 or above installed.
  2. Should be able to hold up to 250 contacts and 6 events per semester without a noticeable sluggishness in performance for typical usage.
  3. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.
  4. Should respond to any user command within 2 seconds under typical load (up to 250 contacts, 6 events).
  5. Should not require an internet connection to operate, since all contact, event, and attendance data is stored and managed locally.
  6. Should not lose previously saved data if the application terminates unexpectedly (e.g. crash, power loss) mid-operation.
  7. Data should be stored in a human-editable, non-proprietary file format (not a DBMS), so users can back up, inspect, or migrate their data manually.
  8. Should be shipped as a single JAR file that does not require a separate installer.
  9. A first-time user with no prior experience should be able to complete the in-app tutorial and add their first contact within 10 minutes.
  10. The colour-coding feature should not be the sole means of distinguishing contact categories, so the app remains usable by colour-blind users (e.g. tags are also shown as text).

Glossary

  • Archive: To move a contact or event out of the active list without permanently deleting it, so that it can still be retrieved later.
  • Assigned member: A contact who has been assigned to a particular event. Also referred to as a member of that event.
  • Attendance status: Whether an assigned member was present or absent at an event.
  • CCA (Co-Curricular Activity): A student club or society in a university, such as a band, sports team or interest group.
  • CLI (Command Line Interface): A way of using the app by typing text commands, as opposed to clicking buttons in a graphical interface.
  • Colour-code: To assign a colour to a contact so that contacts of the same role or group can be recognised visually.
  • Committee handover: The transfer of responsibilities and information from an outgoing EXCO to the incoming EXCO.
  • Contact: A person saved in CoordiMate, with details such as name, phone number, email address and role.
  • Custom tag: A tag created by the user, to categorise contacts in ways not covered by the default tags.
  • Default tag: A tag that is available without the user creating it: EXCO, Sponsor, UniversityStaff and Logistics.
  • Member ID: A unique, permanent positive integer assigned to a contact, displayed as ID: <number>, and used to identify them in commands across searches, filters, and restarts.
  • Duplicate contact: A contact with the same name (ignoring case and surrounding spaces), normalised phone number, or email address as another saved contact.
  • Event: An activity organised by the CCA, such as a concert or fair, with a unique name, a start date/time and an end date/time.
  • Event lead: An EXCO member who is in charge of organising a particular event.
  • EXCO (Executive Committee): The group of students elected to lead and run a CCA.
  • External contact: A contact from outside the CCA, such as a sponsor, university staff member, or EXCO member of a collaborating CCA.
  • Future event: An event whose start date/time is later than the current date/time.
  • Internal contact: A contact from within the CCA, such as a member, fellow EXCO member or advisor.
  • JAR file: A single file that packages a Java application so that it can be run without installation.
  • Local data file: The file on the user's computer where CoordiMate automatically saves all contacts, events and attendance records.
  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Normalised phone number: A phone number with spaces, hyphens and brackets removed, used to detect duplicates. For example, +65 9123 4567 and +6591234567 are the same.
  • On leave: A temporary status marking a contact as unavailable until a specified date, after which it is cleared automatically.
  • Organisation: The external company or body that a contact belongs to, such as a sponsor company or university office.
  • Prefix: The short label before a value in a command that tells CoordiMate which field it belongs to, such as n/ for name or t/ for tag.
  • Role: A contact's responsibility or position in relation to the CCA, such as Logistics Lead or Vice-President.
  • Tag: A short label attached to a contact to categorise it, such as EXCO or Sponsor. A contact can have multiple tags.
  • Telegram handle: A user's username on the Telegram messaging app, such as @aishatan.
  • Tutorial: An in-app guide that introduces a first-time user to CoordiMate's key features.
  • Typical usage: Using CoordiMate with up to 250 contacts and 6 events, as described in the NFRs.
