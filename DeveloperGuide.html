Design

Logic component

API : Logic.java

  1. CoordiMateParser selects a command parser, such as DeleteCommandParser, to produce a Command subclass.
  2. LogicManager executes it. Most data changes run on a model copy, committed only after saving atomically.
  3. Logic returns the resulting CommandResult.

For execute("delete 1"), the first call resolves the contact and requests confirmation. The next input deletes it only if it is y or Y; anything else cancels.

Every error message is followed by the usage of the command that failed. CoordiMateParser adds it to parse errors and LogicManager adds it to execution errors, using Messages.withUsage.

Parameter detection

Command parsers detect parameter-like text before validating field values. Consequently, a field's allowed characters alone do not determine which values can be entered through the CLI. Prefix matching is case-insensitive.

ParameterSyntax defines the shared parameter boundary: the start of the input or a position immediately after whitespace, using StringUtil.WHITESPACE_CHARACTERS for Java whitespace and Unicode White_Space. It also defines the event-style pattern. PrefixParser reuses that boundary and pattern, and defines the contact-style pattern with the relationship-word exception:

Detection rule Parameter-like text at a boundary Used by
Contact-style letters/, except standalone s/o and d/o, ignoring case Contact add/edit/delete, tag commands, and markattendance
Event-style letters/, without the relationship-word exception Event add/edit/delete/archive and the shared EventContactsParser used by assign, unassign, and members

A supported prefix starts a parameter; an unsupported token is rejected as an unknown parameter. Repeated and empty parameters are then handled according to the command. Contact and tag parsers, along with the shared EventContactsParser used by assign, unassign, and members, use ArgumentTokenizer to extract values after rejecting unknown parameters. PrefixParser#parseUniqueParameters also splits values and rejects repeated parameters for its callers.

The examples below are argument fragments; other required arguments must still be supplied:

Fragment Result
r/Lead/Deputy The internal slash stays in the role value, which passes role validation.
r/Lead Deputy/Assistant Deputy/ follows whitespace and is rejected as an unknown parameter.
m/Discuss r/Lead r/ starts a role parameter rather than remaining in the note.
n/Ravi s/o Kumar The standalone relationship word is exempt from contact-style detection and is allowed by name validation.
evn/Concert/Workshop The internal slash stays in the event name.
evn/Concert Workshop/Music Workshop/ follows whitespace and is rejected as an unknown parameter.

The s/o and d/o exemption applies throughout contact-style argument scanning, not only inside name fields. It does not change field validation: names allow slashes only in these standalone relationship words and need at least one letter outside them, whereas roles and organisations allow other slashes. Phones, emails, tags, and date fields reject slashes even when parameter detection leaves them in the value.

markattendance currently uses contact-style detection for both its event and member names. Its event-name parsing therefore accepts evn/Concert s/o Kumar, which event-style commands reject. Passing parsing does not guarantee execution: the event and member must still exist. This describes the current parser difference rather than a design requirement for event names.

Quotation marks do not disable parameter detection in contact, tag, or event commands. For example, r/"Lead Deputy/Assistant" still detects Deputy/; these commands provide no general quoting or escaping mechanism for parameter-like text inside values.

Both detection styles retain slash-leading words such as /st and /Workshop: evn/Concert /Workshop names an event Concert /Workshop. /st and /et are not aliases for st/ and et/: they fail date validation in date fields or cause missing-parameter errors when replacing required prefixes, but can remain literal in names. Startup cleanup shares ParameterSyntax's pattern and preserves these names.

filter and search use separate parsers:

  • FilterCommandParser detects letters/ at the same boundaries, with no s/o or d/o exemption. Tokens inside double quotes are ignored during detection, so filter organisation/"NUS docs/team" keeps docs/team in the value, while the unquoted form rejects docs/. Filter values are checked for non-emptiness and later resolved against saved data, rather than passed through the corresponding model field validators. See Filtering contacts.
  • SearchCommandParser treats the remaining arguments as a keyword, optionally removes surrounding double quotes, and normalises whitespace. It does not detect parameters, so slash-containing text remains keyword text.

Model component

API : Model.java

Model has no dependencies on UI, Logic, or Storage. It holds:

  • contacts in UniquePersonList, with immutable MemberIds. CoordiMate allocates IDs; UniquePersonList rejects duplicates and preserves IDs on replacement or editing.
  • a global tag list, unique ignoring case. Adding, editing, or replacing contacts registers missing tags and keeps unused tags.
  • events, whose ordered member lists contain contact Names. CoordiMate updates these names when contacts are renamed and removes them when contacts are deleted.
  • an unmodifiable ObservableList<Person> of filtered contacts, such as search results, for UI observation and binding.
  • an archive view controlling whether contact and event lists show active or archived items.
  • UserPrefs, exposed as ReadOnlyUserPrefs: window size, position, maximized state, and tutorial completion or dismissal.

Note: Each Person holds Tag objects compared by value with the global UniqueTagList, not necessarily shared instances. The alternative below shares the global objects, keeping one Tag instance per unique tag.

Storage component

API : Storage.java

StorageManager reads and writes model data as JSON through JsonCoordiMateStorage and JsonUserPrefsStorage. JsonSerializableCoordiMate stores separate contact (JsonAdaptedPerson), event (JsonAdaptedEvent), and global tag (JsonAdaptedTag) lists. Contacts also store their tags; events identify members by contact name, not ID.

MainApp resolves data and preferences paths, and LogsCenter resolves the log path, against FileUtil#getHomeFolder(): the running JAR's folder, or the working directory when run from an IDE or Gradle. Files therefore stay in the same home folder regardless of the JAR's launch directory.

Loading validates saved data without overwriting invalid files. An unreadable data file triggers a warning naming the file, then closes the app for repair or restoration. Unreadable preferences alone cause default preferences to be used without saving them that session. Legacy data, including files without member IDs or a tag list, loads and is migrated on the next save.

Startup event cleanup

Before loading the model, MainApp calls StorageManager#cleanUpEventNames() to migrate saved events, including archived events. The cleanup:

  • deletes events whose names contain whitespace followed by parameter-like text, such as c/review, because those names cannot be used in event commands;
  • renames later events whose names were distinct under legacy whitespace rules but now match, ignoring case, with an available suffix such as (2). Long names are shortened to fit the 100-character limit. Duplicates under the legacy rules remain invalid;
  • deletes events with a start or end date in year 0000, and removes year-0000 reminder dismissal history from events that remain.

Renamed events keep their members, attendance, reminder dismissal history (except year-0000 entries), and archive status. The remaining data is validated before the cleanup is saved using saveCoordiMateIfUnchanged, under a DataFileGuard lock. If validation or saving fails, the original file is left unchanged. If no cleanup is needed, the file is not rewritten. A startup warning reports deleted and renamed events after a successful save.

Permanent member IDs

The member ID implementation uses MemberId, MemberIdResolver, and the persisted nextMemberId counter.

Allocation and editing

CoordiMate allocates immutable IDs from the increasing nextMemberId counter. UniquePersonList rejects duplicates and ID changes on editing. Deleted IDs are never reused; clear starts a new dataset at 1.

Below, three contacts were added, ID 3 was deleted, and a fourth was added with ID 4. nextMemberId is now 5.

Command targeting

ParserUtil#parseMemberId parses a positive integer; MemberIdResolver searches all saved contacts, including those hidden by searches, filters, or the archive view. Unknown IDs are rejected without changes. Since events use names internally, assign and unassign resolve every ID before translating them to names.

delete retains the resolved contact during confirmation, then resolves its ID again and rejects removed or edited contacts.

Storage and migration

The data file stores memberId and nextMemberId. Legacy contacts without IDs receive consecutive IDs in file order, after existing IDs. Allocation alone does not rewrite the file; the next successful save, possibly startup cleanup, records the IDs. Duplicate or invalid IDs make the file invalid.

Member ID design considerations

ID allocation Benefit Cost
Saved counter (chosen) Never reuses deleted IDs, including the highest Requires validation and migration
Highest saved ID plus one at launch No extra saved state Reuses the highest ID after deletion and restart

Saving data atomically

Contact, event-detail, tag, and attendance changes take effect in both the app and data file, or neither. Read or write failures leave both unchanged.

Atomic save flow

1. Execute on a model copy. LogicManager#execute routes data changes such as AddCommand, EditCommand, and AssignCommand through LogicManager#executeAtomicCommand:

  1. Check that the data file remains loadable. Reject unreadable data without overwriting it; a missing file is allowed.
  2. Copy live data into a candidate ModelManager. Preserve the archive view and contact filter using candidate.updateFilteredPersonList(model.getFilteredPersonList()::contains), so commands reading the displayed list see the same contacts.
  3. Execute the command on the candidate; discard it on failure.
  4. Save the candidate; reject and discard it if saving fails or another window has changed the file since loading.
  5. Replace live data with the saved candidate, updating the UI.

The live model changes only at step 5. Afterwards, add and edit clear the contact filter to reveal the changed contact.

Note: Add new data-changing command classes to LogicManager#execute's fixed list to use this atomic path.

Successful executeAtomicCommand(c) for an AddEventCommand, omitting parsing:

2. The data file is replaced in one step. JsonCoordiMateStorage#saveCoordiMate writes to a temporary file in the same folder, then replaces the data file using ATOMIC_MOVE and REPLACE_EXISTING. Under the Java API contract, atomic replacement depends on the filesystem provider. Unsupported moves throw AtomicMoveNotSupportedException; there is no non-atomic fallback.

Where supported, process termination while the OS remains running leaves the old or new complete target, possibly with a leftover temporary file. Saves do not force file contents or directory metadata to durable storage, so OS crashes and power loss have no recovery guarantee. JsonUserPrefsStorage writes preferences directly, without atomic replacement.

Confirmed delete uses this path. Read-only commands (list, search, filter, members) run on the live model without saving. Reminder dismissal has its own save path.

Atomic save design considerations

Commit strategy Benefit Cost
Copy, save, then replace (chosen) No command-specific rollback; UI never shows unsaved edits Copies all data per command, acceptable at typical load
Execute live; restore a snapshot on failure No copy on successful saves UI briefly shows changes that are then reverted

Event reminders

The Upcoming events panel lists reminders for events starting soon, ordered by start time and then by name.

Reminder calculation and dismissal

Reminders are derived from saved events, not stored separately.

Finding upcoming events. UpcomingEventFinder uses a testable Clock to select eligible events:

  • Timed starts qualify from 24 hours before the start through the start itself, inclusive.
  • Date-only starts qualify throughout the preceding day and start date.

Results are ordered by start, then name ignoring case. Date-only starts count as midnight only for ordering.

Keeping the reminder list current. ReminderService holds ReminderPanel's observable list. ReminderService#refreshReminders() excludes archived and dismissed events from the finder's results. It runs at LogicManager creation, after every command (including failures, through LogicManager#execute's finally block), every minute via MainWindow's Timeline, and when the main window is shown after being hidden. The list is replaced only when its contents change, avoiding unnecessary redraws.

Remembering dismissals. Event#isReminderDismissed() checks the current start against dismissedReminderStarts, saved with each event so dismissals survive restarts. Renaming or changing only the end preserves dismissal. Event#withDetails, used by editevent, clears history on any start change, including a return to an earlier start, allowing the new reminder to appear.

Dismissing a reminder. dismiss INDEX and Dismiss use the same ReminderService, created by LogicManager and passed to DismissCommand. The sequence shows dismiss 1 on save success and failure.

DismissCommand resolves the index against the last displayed list, rejects reminders no longer upcoming, and asks the service to dismiss it. The service saves a copy before updating the live event, preserving details, members, and attendance. Storage#saveCoordiMateIfUnchanged rejects files changed by another window.

On read or save failure, including conflicts, dismissal still hides the reminder for this session and returns a Not saved warning; it may reappear after restart. Since the service saves directly, dismiss bypasses executeAtomicCommand.

Reminder design considerations

Decision Benefit Cost
Refresh every minute and after commands (chosen) Simple; reads current time after sleep or clock changes; event edits need no extra refresh code Reminders can appear or expire up to a minute late
Timer per eligibility change Exact update time Event edits must reschedule timers; sleep or clock changes can mistime them
Store dismissed starts (chosen) Saved with the event; a different start no longer matches, even if code bypasses Event#withDetails Extra field per event
Store a dismissed flag Simpler data Every start-changing path must clear it or leave a moved event dismissed

Event attendance

Attendance data and updates

An Event is immutable. It stores:

  • List<Name> members in assignment order.
  • Map<Name, AttendanceStatus> attendance: PRESENT or ABSENT; no entry means unmarked.

The constructor rejects attendance for non-members. MarkAttendanceCommand resolves the event and member ignoring case, rejects an unchanged status, or replaces the event using Event#withAttendance. It runs through executeAtomicCommand.

Its parser uses contact-style parameter detection, including for the event name; see that section for the difference from other event commands.

Change Effect on attendance
assign adds members Existing attendance is kept. New members are not marked.
unassign removes members The removed members' attendance is removed.
editevent renames or reschedules the event Attendance is kept.
edit renames a contact The contact's attendance moves to the new name in every event.
delete deletes a contact The contact's attendance is removed from every event.

JSON attendance maps member names to "present" or "absent". A missing field loads as no recorded attendance.

Attendance design considerations

Decision Benefit Cost
Attendance map in each event (chosen) Event, membership, and attendance changes are saved, copied, and replaced together Cross-event attendance queries scan every event
Separate event/contact attendance list Easy cross-event queries for a contact Every event/contact change must update the list to avoid orphaned records
Missing map entry means unmarked (chosen) No new-member data or legacy conversion Derive unmarked counts from members
Explicit NOT_MARKED status Every member has a status Every member addition needs an entry; legacy files need conversion

Filtering contacts

The filter command lists the contacts that match every given FIELD/VALUE pair, where the field is tag, event, or organisation.

Filter parsing and resolution

Parsing needs no saved data; resolving does.

Parsing. FilterCommandParser splits FIELD/ tokens into FilterCriterion records containing a FilterField and value. Quoted values can contain literal FIELD/ text, unlike contact and event commands; see Parameter detection for parser-specific rules.

Resolving. FilterCommand#execute turns each criterion into a Predicate<Person> using the model:

TagFilterPredicate handles tag criteria; EventMembersPredicate handles event criteria. Both implement Predicate<Person>; organisation criteria use a plain lambda.

Field The value must match, ignoring case A contact matches if
tag a tag in Model#getTagList() it has that tag
event the name of a saved event it is a member of the event with that name
organisation the organisation of at least one saved contact its organisation is that value

Unknown values are rejected before changing the display. Otherwise, ContactFilterPredicate implements Predicate<Person> and holds other predicates, combining them with AND (the composite pattern). Model#updateFilteredPersonList receives this composite. filter runs on the live model without saving. The diagram omits the organisation lambda.

The event and tag predicates follow names, including later renames.

To add a filter field, add a constant to FilterField, a case to FilterCommand#resolvePredicate, and a case to the example-selection switch in FilterCommandParser#parse.

Filter design considerations

Decision Benefit Cost
Full fields: filter tag/EXCO event/Final Concert (chosen) Self-explanatory; field names come from one enumeration Differs from short prefixes such as t/
Reuse prefixes: filter t/EXCO evn/Final Concert Consistent with other commands Prefix meanings may differ by command; o/ is easy to confuse
Reject unknown values (chosen) Distinguishes typos from valid groups with no contacts Requires model lookup before filtering
Show an empty list for unknown values Simpler Conceals mistyped values

Keeping events in sync with contacts

Events refer to contact Names because editing replaces Person objects. These references must stay synchronized with saved contacts.

Synchronizing contacts and event views

Renaming and deleting contacts. CoordiMate updates events whenever a contact changes:

  • Renaming replaces the old name in every affected event, preserving position and attendance.
  • Deleting removes the name and attendance from every affected event.

Updated events are built before any changes. An existing member with the new name causes rejection without changes. Loading rejects event members absent from saved contacts.

Showing an event's members. MembersCommand filters the contact list with EventMembersPredicate, which looks up its event by name on each test. assign adds matches; unassign removes them; deleteevent empties the list. After editevent renames an event, LogicManager#keepEventViewsAfterRename replaces the predicate with the new name. filter event/... uses the same predicate and follows these changes.

Similarly, LogicManager#keepTagFiltersAfterRename updates filter tag/... criteria after edittag.

Note: Contact-list changes trigger predicate re-testing. CoordiMate#resetData must therefore replace events before contacts, or event-member views would use stale events.

Event synchronization design considerations

Member reference Benefit Cost
Contact name (chosen) Unique and readable in JSON members Renaming or deleting contacts must update events
Permanent member ID Renaming does not affect events Requires migration of saved membership and attendance, plus name lookups for display

Marking contacts as on leave

Leave status and date refresh

LeaveDate checks leave dates through Person#isOnLeave(LocalDate today) and LeaveDate#covers. Person stores the optional date, set by lv/ in add or edit and cleared by an empty lv/. Input dates cannot be past; loading accepts past dates so ended leave remains readable.

The UI shows On leave until only while leave covers today. Passing the date changes no data: it remains saved until replaced or cleared. Copies made by CoordiMate#setTag, CoordiMate#removeTag, and similar methods must retain it. The activity diagram shows how the UI determines leave status; expired dates remain saved but display as not on leave.

PersonListPanel and EventListPanel use testable Clocks. MainWindow's one-minute reminder timer calls PersonListPanel#refreshIfDateChanged() and EventListPanel#refreshIfDateChanged() to redraw Contacts and Events only after a date change. JSON stores leaveUntil; missing fields mean no leave.

Remove ended dates at launch Only active leave remains saved Requires a startup save and checks while open

Archiving contacts and events

archive, unarchive, archiveevent, and unarchiveevent implement archiving. list archived selects the archive view, and list returns to the active view.

Archive flags and view filtering

The archive flag. Person and Event are immutable and store a boolean archived. withArchived(boolean) returns a copy; all other copies retain the flag. Person's full constructor requires it, forcing callers such as EditCommand and CoordiMate's tag updates to supply it.

Hiding archived items. ModelManager keeps the archive view (true for archived items) separate from command filters. Contacts must match both; events must match the archive view. MainWindow observes it to update tab titles and sidebar commands. Model-level filtering makes search, filter, and members respect the view without command changes.

Below, ArchiveCommand resolves permanent ID 12 regardless of the display and runs on a model copy, like edit.

Keyboard navigation and command history

Non-Functional Requirements

These are acceptance targets, not measured results. Test performance with one CoordiMate instance and valid data on writable local storage; record OS, Java version, processor, memory, and dataset. Use timed trials with target users for speed and onboarding targets.

  1. Run on mainstream OS platforms with Java 25, targeting CI configurations. Manually launch the packaged JAR on each target platform before claiming release compatibility.
  2. Store and reload the maximum typical load. Saved contact details, IDs, tags, schedules, assignments, attendance, archive flags, leave dates, and reminder dismissals should survive normal restarts. Assess performance under NFR 4. This is a whole-dataset capacity target, not an enforced limit; data is not partitioned by semester.
  3. For users familiar with CoordiMate's keyboard shortcuts, a short sequence of switching views and selecting adjacent cards should take less time on average using shortcuts than using the mouse. Compare repeated trials by the same user from the same starting view and selection, including keyboard mode changes.
  4. At typical load, every contact, tag, event, attendance, or reminder command should have a median response time of at most 2 seconds over repeated trials on the recorded machine, including delete, unassign, archiveevent, unarchiveevent, dismiss, and clear. Measure Enter to feedback and completed view update, including saving. Exclude startup and confirmation waiting; time the prompt and confirmed response separately.
  5. Contact, tag, event, attendance, archive, reminder, Help, and tutorial features should work offline. The online User Guide requires internet access.
  6. If the app process terminates during saving while the OS runs, an existing valid data file should retain the old or new complete dataset, assuming atomic replacement support. Exclude preferences, OS crashes, power loss, hardware failure, and external file changes.
  7. Store readable JSON that ordinary tools can inspect and back up. Manual edits require the app to be closed and must meet saved-data constraints.
  8. Distribute one application JAR without a CoordiMate installer, assuming Java is installed.
  9. After completing or closing the tutorial, a first-time target user should add a contact within 10 minutes, without another person's help. Supply valid, unique name, phone, email, and role values. Time from input-ready command box to the saved contact's visible details and success message. Include Help, command hints, User Guide consultation, and corrections; exclude installation, launch, and tutorial reading.
  10. Every colour-coded tag should show its name so categories are distinguishable without colour.

Glossary

  • Archive: Hide a contact or event from active lists while preserving details, assignments, and attendance.
  • Assigned member: A contact assigned to an event, also called its member.
  • Attendance status: An assigned member's recorded present or absent value. No record means unmarked, not absent.
  • CCA (Co-Curricular Activity): A university club or society, such as a band, sports team, or interest group.
  • CLI (Command Line Interface): A text-command interface; CoordiMate provides a command box in its graphical window.
  • Colour-coded tag: A tag coloured by name. EXCO, Logistics, Sponsor, and UniversityStaff have distinct built-in colours; others share a default. Users cannot choose tag or contact colours.
  • Command mode: The keyboard mode for entering commands in the command box.
  • Committee handover: Transfer of responsibilities and information between outgoing and incoming EXCOs.
  • Contact: A saved person identified by member ID.
  • Custom tag: A user-created contact category beyond the default tags.
  • Default tag: A built-in tag: EXCO, Sponsor, UniversityStaff, or Logistics.
  • Duplicate contact: A contact with the same name (ignoring case and normalising spaces), normalised phone number, or email address (ignoring case) as another saved contact, including an archived one.
  • Event: A saved CCA activity, such as a concert or fair, with a unique name ignoring case and extra spaces.
  • Event lead: An EXCO member organising an event.
  • EXCO (Executive Committee): Students elected to lead and run a CCA.
  • Future event: An event starting after the current date/time.
  • Home folder: The JAR's folder, containing data, preferences.json, and logs regardless of launch directory. IDE or Gradle runs use the working directory.
  • JAR file: A Java application packaged to run without installation.
  • Local data file: JSON storing the application data in NFR 2, at data/coordimate.json by default, relative to the home folder.
  • Mainstream OS: Windows, macOS, or Linux.
  • Member ID: A contact's unique, permanent positive integer, displayed as ID: <number> and used across searches, filters, and restarts.
  • Navigation mode: The keyboard mode in which key presses browse cards and switch views.
  • Normalised phone number: A phone number with the optional +, spaces, hyphens and brackets removed, used to detect duplicates. For example, +65 9123 4567 and 6591234567 are the same.
  • On leave: Unavailable through the saved leave end date, inclusive, using the computer's local date.
  • Organisation: A contact's company or body, such as a CCA, sponsor, or university office.
  • Parameter-like text: Text shaped like [whitespace][letters]/ (e.g. r/) that a parser may treat as a parameter, not part of a value. The brackets are descriptive: whitespace includes spaces, tabs, Java whitespace and Unicode White_Space; letters are consecutive ASCII letters (A-Z or a-z) adjacent to the slash. Preceding whitespace is unnecessary at the start of the arguments; whitespace after the slash is not required. See Parameter detection for command-specific rules and exceptions.
  • Prefix: A command field label, such as n/ for name or t/ for tag.
  • Reminder: An in-app notice for an upcoming, active event. Timed starts qualify from 24 hours before start through start time; date-only starts qualify on the preceding day and start date. Refreshes at startup, after commands, and every minute while the app runs.
  • Role: A contact's responsibility or position in relation to the CCA, such as Logistics Lead or Vice-President.
  • Tag: A contact category such as EXCO or Sponsor; contacts can have multiple tags.
  • Tutorial: An in-app introduction to CoordiMate's views, commands, and keyboard navigation.
  • Typical load: A local dataset of up to 250 contacts and 6 events in total, including archived items, with up to 250 assigned members and their attendance records per event.
