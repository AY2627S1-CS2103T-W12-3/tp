Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

UI component

The API of this component is specified in Ui.java.

The first diagram shows the parts created or used by MainWindow, including CommandBox, ResultDisplay, PersonListPanel, EventListPanel, ReminderPanel, StatusBarFooter, and TutorialWindow. MainWindow also uses TagListViewModel to keep the Tags view synchronized with contact and tag data.

The inheritance diagram shows all ten subclasses of the abstract UiPart, which captures behavior shared by visible GUI parts. Each UiPart box represents the same superclass, repeated to keep the arrows clear. TagListViewModel and WindowBounds are helpers rather than UiPart subclasses.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

Besides the main window, the UI component provides:

  • HelpWindow, a command quick reference built from the command words of the command classes.
  • TutorialWindow, which renders the tutorial overlay. UiManager opens it on first launch, and the tutorial command or F2 opens it again.
  • Command history in CommandBox, which keeps the commands entered in the current session for recall with the Up and Down arrow keys.

At launch, MainWindow restores the window size, position, and maximized state saved in GuiSettings, using WindowBounds to keep the window within the available screen area.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data. For example, the Contacts, Events, and Tags views refresh when a contact they show is edited.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands. A command can ask MainWindow to show the Help window, the tutorial, or a particular view through its CommandResult.
  • depends on some classes in the Model component because it displays Person and Event objects from the model.

Logic component

API : Logic.java

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a CoordiMateParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand), which is executed by the LogicManager.   3. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Model component

API : Model.java

The Model component,

  • stores CoordiMate data, including all Person objects (which are contained in a UniquePersonList object).
  • assigns each saved Person an immutable MemberId. CoordiMate maintains the next ID to allocate, and UniquePersonList rejects duplicate IDs. Replacing or editing a contact preserves its ID.
  • stores a case-insensitively unique global tag list. Every tag assigned to a contact is also registered in this list; adding, editing, or replacing contacts registers any missing tags while preserving existing unused tags.
  • stores all Event objects. Each Event records its assigned members as an ordered list of contact Names. CoordiMate keeps these lists in sync with the contacts: deleting a contact removes their name from every event, and renaming a contact updates it.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • keeps an archive view, which decides whether the filtered contact list and the filtered event list show active or archived items.
  • stores a UserPrefs object that represents the user’s preferences, including window size and position, maximized state, and whether the first-launch tutorial has been completed or dismissed. This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: CoordiMate already keeps a global UniqueTagList, but each Person holds its own Tag objects, which are compared with those in the list by value and are not necessarily the same objects. The alternative, arguably more object-oriented, design below has each Person reference the Tag objects in that list instead, so CoordiMate maintains exactly one Tag object per unique tag.

Storage component

API : Storage.java

The Storage component,

  • can save both CoordiMate data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonCoordiMateStorage and JsonUserPrefsStorage (one class per data file).
  • converts CoordiMate data through JsonSerializableCoordiMate, which stores contacts (JsonAdaptedPerson), events (JsonAdaptedEvent), and the global tag list (JsonAdaptedTag) as separate lists. Each contact also stores its own tags, and each event records its members by contact name rather than by member ID.
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Saved data is validated when it is loaded, and a file that fails validation is never overwritten. If the data file cannot be loaded, CoordiMate shows a warning naming the file and then closes, so that the user can repair or restore it. If only the preferences file cannot be loaded, CoordiMate starts with default preferences and does not save them for that session. Data files saved by earlier versions, such as those without member IDs or a saved tag list, are still accepted and are updated the next time the data is saved.

Common classes

Classes used by multiple components are in the coordimate.commons package. These include GuiSettings, LogsCenter, the shared exceptions such as DataLoadingException, and utilities such as StringUtil and JsonUtil.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Permanent member IDs

The member ID implementation uses MemberId, MemberIdResolver, and the persisted nextMemberId counter.

Allocation and editing

Person holds an immutable ID. CoordiMate allocates new IDs from a nextMemberId counter, which only ever increases, so deleted IDs are never reused. UniquePersonList rejects duplicate IDs and prevents an edit from changing a contact's ID. clear starts a new empty dataset and resets allocation to 1.

The object diagram below shows the contacts after three contacts were added, the contact with ID 3 was deleted, and another contact was added. The new contact received ID 4, and nextMemberId moved on to 5, so ID 3 stays unused.

Command targeting

ParserUtil#parseMemberId parses a positive integer, and MemberIdResolver looks it up among all saved contacts, including contacts hidden by the current search, filter, or archive view. An unknown ID is rejected without changing data. Event membership and attendance still use contact names internally, so assign and unassign translate IDs to names after resolving every ID.

delete keeps the resolved contact while waiting for confirmation. On confirmation, it resolves the ID again and rejects the deletion if that contact has since been removed or edited.

Storage and migration

The data file stores each contact's memberId and the nextMemberId counter. When a file saved before member IDs existed is loaded, contacts without an ID receive consecutive IDs in file order, after any IDs already in the file. Loading does not rewrite the file; the IDs are recorded on the next successful save. A file with duplicate or invalid IDs is rejected like any other invalid data file.

Design considerations

Aspect: How the next ID is chosen

  • Alternative 1 (current choice): Save a counter in the data file.

    • Pros: An ID is never reused, even after the highest-numbered contact is deleted.
    • Cons: The counter must be validated and migrated along with the contacts.

  • Alternative 2: Use one more than the highest saved ID on every launch.

    • Pros: Nothing extra to save.
    • Cons: Deleting the highest-numbered contact and restarting would reuse its ID for a different contact.

Saving data atomically

Commands that edit contacts, event details, tags, or attendance either take effect in full, both in the app and in the data file, or not at all. This keeps the displayed data and the saved data identical even when the data file cannot be read or written.

Implementation

Two mechanisms work together.

1. Commands run on a copy of the model. LogicManager#execute passes commands that change data, such as AddCommand, EditCommand, and AssignCommand, to LogicManager#executeAtomicCommand, which does the following:

  1. It checks that the existing data file can still be loaded. If it cannot, the command is rejected and the file is left untouched, so that the user can repair it. A missing data file is not an error.
  2. It creates a second ModelManager, the candidate, from a copy of the live model's data. It also copies the current archive view onto the candidate, so that commands which read the displayed list see the same contacts on the candidate as on the screen.
  3. It executes the command on the candidate. If the command fails, the candidate is discarded.
  4. It saves the candidate's data. If the file was changed by another CoordiMate window since it was loaded, or the save fails, the command is rejected and the candidate is discarded.
  5. Only then does it replace the live model's data with the candidate's data, which updates the UI.

The live model is not touched until step 5, so a failure at any earlier step leaves the app exactly as it was. Afterwards, add and edit show all contacts again, so that the changed contact is visible.

Note: LogicManager#execute chooses which commands use this path from a fixed list of command classes. A new command that changes data must be added to that list, or its changes will not be saved atomically.

2. The data file is replaced in one step. JsonCoordiMateStorage#saveCoordiMate writes the new data to a temporary file in the same folder, then moves it over the data file with an atomic move. The move requests ATOMIC_MOVE and REPLACE_EXISTING. Under the Java API contract, replacing an existing target with an atomic move depends on the filesystem provider. An unsupported atomic move throws AtomicMoveNotSupportedException; this code has no fallback to a non-atomic overwrite.

When atomic replacement is supported, a process-only interruption leaves the existing target at either the old or new complete version while the OS remains running. An interruption can leave a temporary file behind. The save path does not explicitly force file contents or directory metadata to durable storage, so this mechanism does not establish recovery guarantees after an OS crash or power loss. User preferences use a separate, direct JSON write through JsonUserPrefsStorage and do not have this atomic-replacement protection.

A confirmed delete runs through executeAtomicCommand like any other command. Commands that do not change data, such as list, search, filter, and members, run directly on the live model without saving. Reminder dismissal uses its own save path, described in Event reminders.

Design considerations

Aspect: How a command is prevented from taking effect when saving fails

  • Alternative 1 (current choice): Execute the command on a copy of the model, save the copy, then replace the live model's data.

    • Pros: Works for every command that changes data without command-specific rollback code. The UI never shows an edit that was not saved.
    • Cons: Copies all data for each command, which is acceptable for the expected typical load.

  • Alternative 2: Execute the command on the live model, and restore a snapshot if saving fails.

    • Pros: No copy is needed when saving succeeds.
    • Cons: The UI observes the model, so it briefly shows a change that is then reverted.

Event reminders

The Upcoming events panel lists reminders for events starting soon, ordered by start time and then by name.

Implementation

Reminders are worked out from the saved events whenever they are needed, rather than being stored.

Finding upcoming events. UpcomingEventFinder decides which events qualify, using a Clock so that tests can fix the current time:

  • An event with a start time qualifies from 24 hours before its start until the start itself, inclusive.
  • An event with only a start date qualifies throughout the day before that date and the date itself.

It returns the qualifying events ordered by start, then by name ignoring case. A date-only start counts as midnight for ordering only.

Keeping the reminder list current. ReminderService holds the observable list that ReminderPanel displays. ReminderService#refreshReminders() rebuilds it from the finder's results, leaving out archived events and events whose reminder has been dismissed. The list is refreshed:

  • when LogicManager is created, so reminders are ready at launch.
  • after every command, in a finally block of LogicManager#execute, so that adding, editing, archiving, or deleting an event updates the panel straight away, even if the command fails.
  • once a minute by a Timeline in MainWindow, so that reminders appear and expire as time passes.
  • when the main window is shown again after being hidden.

The list is only replaced when its contents change, which avoids redrawing the panel every minute.

Remembering dismissals. Each Event stores the start values whose reminders were dismissed, in dismissedReminderStarts. Event#isReminderDismissed() checks whether the current start is among them, so a dismissal applies to one particular start:

  • Renaming the event or changing only its end keeps the dismissal, because the start is unchanged.
  • Event#withDetails, used by editevent, clears the history whenever the start changes, including a change back to an earlier start. The reminder for the new start can then appear.

The history is saved with the event, so a dismissal survives restarting the app.

Dismissing a reminder. dismiss INDEX and the panel's Dismiss button both hide a reminder through the same ReminderService, which LogicManager creates and passes to DismissCommand.

The sequence diagram below shows dismiss 1, both when the dismissal is saved and when saving fails.

DismissCommand checks the index against the current reminder list, then asks ReminderService to dismiss that event's reminder. Like other commands that change data, the service saves an updated copy of the event before changing the live event, and keeps the event's details, members, and attendance unchanged.

If the data file cannot be read or saved, the dismissal is still kept for the current session, so the reminder disappears, and the command shows a Not saved warning instead of an error. The reminder may then return after a restart. Because ReminderService handles the save itself, LogicManager does not run dismiss through executeAtomicCommand.

Design considerations

Aspect: How reminders follow the passage of time

  • Alternative 1 (current choice): Recompute the reminders once a minute, and after every command.

    • Pros: Simple, and correct after the computer sleeps or its clock changes, since each refresh reads the current time. Adding, editing, and deleting events need no extra code to update reminders.
    • Cons: A reminder can appear or disappear up to a minute late.

  • Alternative 2: Schedule a timer for each event's next eligibility change.

    • Pros: Reminders change at exactly the right moment.
    • Cons: Every event change must cancel and reschedule its timers, and timers can fire at the wrong moment after a sleep or clock change.

Aspect: How a dismissal is remembered

  • Alternative 1 (current choice): Store the dismissed start values in the event.

    • Pros: The dismissal is saved with the event, and naturally stops applying when the start changes.
    • Cons: Adds a field to every event in the data file.

  • Alternative 2: Store a single "dismissed" flag in the event.

    • Pros: Simpler data.
    • Cons: The flag would have to be cleared on every change to the start, and a moved event could otherwise stay silently dismissed.

Event attendance

Implementation

An Event is immutable. It stores:

  • its members as a List<Name> of contact names, in the order they were assigned.
  • its attendance as a Map<Name, AttendanceStatus>, where AttendanceStatus is an enumeration of PRESENT and ABSENT. A member with no entry in the map has not been marked.

The Event constructor rejects an attendance record that contains a name which is not a member, so attendance can never exist for someone who is not assigned to the event.

MarkAttendanceCommand finds the event and the member, ignoring case, and reports that no changes were made if the member already has the requested status. Otherwise it replaces the event with a copy from Event#withAttendance. The command changes data, so it runs through executeAtomicCommand as described above.

Other commands keep the attendance record consistent with the members:

Change Effect on attendance
assign adds members Existing attendance is kept. New members are not marked.
unassign removes members The removed members' attendance is removed.
editevent renames or reschedules the event Attendance is kept.
edit renames a contact The contact's attendance moves to the new name in every event.
delete deletes a contact The contact's attendance is removed from every event.

In the data file, each event stores attendance as an attendance object that maps each member's name to "present" or "absent". A file without this field loads with no attendance recorded.

Design considerations

Aspect: Where attendance is stored

  • Alternative 1 (current choice): Each Event stores a map from member name to status.

    • Pros: An event and its attendance are saved, copied, and replaced as one unit, so they cannot disagree. Removing a member and their attendance is a single change.
    • Cons: A contact's attendance across events can only be found by looking through every event.

  • Alternative 2: Store attendance records in a separate list, each referring to an event and a contact.

    • Pros: Makes it easy to query one contact's attendance across all events.
    • Cons: Every change to an event or contact must also update the separate list, or records are left behind.

Aspect: How "not marked" is represented

  • Alternative 1 (current choice): A member with no entry in the map is not marked.

    • Pros: Newly assigned members need no extra data, and older data files load without conversion.
    • Cons: Code that counts statuses must derive the not-marked count from the members.

  • Alternative 2: Add a third NOT_MARKED status and give every member an entry.

    • Pros: Every member has an explicit status.
    • Cons: Every command that adds a member must also add an entry, and older data files would need converting.

Filtering contacts

The filter command lists the contacts that match every given FIELD/VALUE pair, where the field is tag, event, or organisation.

Implementation

Filtering is split into parsing, which does not need saved data, and resolving, which does.

Parsing. FilterCommandParser splits the arguments at each FIELD/ token into a list of FilterCriterion records, each holding a FilterField and its value. A value may be wrapped in quotation marks, so that it can contain text that looks like a FIELD/ token.

Resolving. FilterCommand#execute turns each criterion into a Predicate<Person> using the model:

Field The value must match, ignoring case A contact matches if
tag a tag in Model#getTagList() it has that tag
event the name of a saved event it is a member of the event with that name
organisation the organisation of at least one saved contact its organisation is that value

If a value matches nothing, the command is rejected before the displayed list is changed. Otherwise the predicates are combined into a ContactFilterPredicate, which a contact matches only if it matches every predicate, and passed to Model#updateFilteredPersonList. filter does not change data, so it is executed directly on the live model.

The class diagram below shows how these classes relate. The organisation criterion is a plain lambda, so it is not shown.

The event and tag predicates identify their event or tag by name. How a filtered list follows later changes to that event or tag is described in Keeping events in sync with contacts.

To add a filter field, add a constant to FilterField, a case to FilterCommand#resolvePredicate, and a case to the example-selection switch in FilterCommandParser#parse.

Design considerations

Aspect: Syntax of a filter

  • Alternative 1 (current choice): Full field names, as in filter tag/EXCO event/Final Concert.

    • Pros: The fields are self-explanatory, and a field is added by extending one enumeration.
    • Cons: Differs from the short prefixes of other commands, such as t/.

  • Alternative 2: Reuse the existing prefixes, as in filter t/EXCO evn/Final Concert.

    • Pros: Consistent with other commands.
    • Cons: Some prefixes would mean different things in different commands, and organisation would need o/, which is easy to confuse with other single-letter prefixes.

Aspect: What happens when a value does not exist

  • Alternative 1 (current choice): Reject the command with an error.

    • Pros: Distinguishes a mistyped value from a valid value that no contact has.
    • Cons: The command must look the value up in the model before filtering.

  • Alternative 2: Show an empty list.

    • Pros: Simpler to implement.
    • Cons: The user cannot tell whether the value was mistyped.

Keeping events in sync with contacts

An event refers to its members by contact Name, not by Person object. Contacts are replaced with new Person objects whenever they are edited, so a name is the stable way to refer to one. In exchange, the app must keep the names in events consistent with the saved contacts.

Implementation

Renaming and deleting contacts. CoordiMate updates events whenever a contact changes:

  • When a contact is renamed, every event that lists the old name is replaced with a copy that lists the new name in the same position, with the contact's attendance carried over.
  • When a contact is deleted, every event that lists the contact is replaced with a copy without the name or its attendance.

All the updated events are built before anything is changed. If an event already has a member with the new name, the rename is rejected and no data is changed. When loading, a data file in which an event lists a member who is not a saved contact is rejected.

The activity diagram below summarises how CoordiMate handles a renamed or deleted contact.

Showing an event's members. MembersCommand filters the contact list with EventMembersPredicate, which holds the event's name and looks the event up each time it is tested. The displayed members therefore follow later changes:

  • After assign or unassign, an added member matches and a removed member no longer does.
  • After deleteevent, no event has that name, so the list becomes empty.
  • After editevent renames the event, LogicManager#keepEventViewsAfterRename replaces the predicate with one for the new name.

filter event/... uses the same predicate, so a filtered list follows the same changes. In the same way, after edittag renames a tag, LogicManager#keepTagFiltersAfterRename updates any filter tag/... criterion to the new name.

Note: A filtered list re-tests its predicate only when the contact list changes. For this reason CoordiMate#resetData replaces the events before the contacts, so that the predicate already sees the new events when it is tested again. Reversing this order would leave event member views out of date.

Design considerations

Aspect: How an event refers to its members

  • Alternative 1 (current choice): By contact name.

    • Pros: Readable in the data file, where members is a list of names. Names are already unique among contacts.
    • Cons: Renaming or deleting a contact must update every event, as described above.

  • Alternative 2: By the contact's permanent member ID.

    • Pros: Renaming a contact would not affect events.
    • Cons: Requires migrating event member and attendance references from names to IDs in the data file, and looking up contacts to display member names.

Marking contacts as on leave

Implementation

LeaveDate implements the date check for the on leave status. Person stores it as an optional field, like birthday and note, which is set with lv/ in add and edit, and cleared with an empty lv/. Person#isOnLeave(LocalDate today) delegates the date comparison to LeaveDate#covers.

A date entered with lv/ must not be in the past, but any real date is accepted when loading the data file, so that leave which has ended can still be loaded.

How leave ends. Nothing is changed when a leave date passes. Instead, the UI asks each contact whether it is on leave on the current date, and shows the On leave until badge only if it is. The ended date stays in the data file until the user replaces or clears it. Code that copies a contact, such as CoordiMate#setTag and CoordiMate#removeTag, must pass the leave date on so that it is not dropped.

The state diagram below shows how a contact's leave changes. Leave ended looks the same as Not on leave in the app; the difference is only that the old date is still saved.

PersonListPanel reads the current date from a Clock, which tests replace to control the date. A window left open past midnight still needs redrawing, so MainWindow's existing one-minute reminder timer also calls PersonListPanel#refreshIfDateChanged(), which redraws the contacts only when the date has changed.

In the data file, the date is stored in a leaveUntil field. Contacts without this field load as not on leave.

Design considerations

Aspect: How leave ends once its date has passed

  • Alternative 1 (current choice): Keep the date, and check it against the current date whenever a contact is displayed.

    • Pros: No data needs changing when leave ends, so no save is needed at launch or at midnight. The behaviour is easy to test by passing a fixed date to Person#isOnLeave.
    • Cons: Ended dates remain in the data file, and a window left open past midnight must be redrawn.

  • Alternative 2: Remove ended leave dates from the data, for example at launch.

    • Pros: The data file only contains leave that is still active.
    • Cons: Requires saving at launch, which no other feature does, and still needs a check for leave that ends while the app is open.

Aspect: How an open window notices that the date has changed

  • Alternative 1 (current choice): Check the date on each tick of the existing one-minute reminder timer.

    • Pros: Adds no new timer. Still works if the computer sleeps through midnight or its clock changes.
    • Cons: The badge can stay visible for up to a minute after midnight.

  • Alternative 2: Schedule a timer for the next midnight, then reschedule it each day.

    • Pros: Updates exactly at midnight.
    • Cons: A second timer to manage, which can fire at the wrong time after a sleep or clock change.

Archiving contacts and events

archive, unarchive, archiveevent, and unarchiveevent implement archiving. list archived selects the archive view, and list returns to the active view.

Implementation

The archive flag. Person and Event each have a boolean archived field. Both are immutable, so archiving returns a copy from withArchived(boolean), and every other copy method passes the flag on. Person takes archived as a parameter of its full constructor, which every copy of an existing contact uses, so the compiler makes each copy, such as EditCommand and the tag updates in CoordiMate, pass the flag on.

Hiding archived items. ModelManager keeps an archive view, which is true while archived items are shown, separately from the contact filter set by commands. The filtered contact list shows a contact only if its archived value matches the view and it matches the command's filter. The filtered event list shows the events whose archived value matches the view. MainWindow observes the view to update the tab titles and sidebar commands.

Because the view is applied inside the model, search, filter, and members hide archived contacts without any change to those commands.

The sequence diagram below shows archive 12. ArchiveCommand finds the contact by its permanent member ID, so the command works whatever the displayed list shows. Like edit, it runs on a copy of the model, as described in Saving data atomically.

Effects on other features.

Feature Effect of archiving
Reminders Archived events have no reminders.
assign Rejected for an archived event or an archived contact.
unassign Rejected for an archived event, but can still remove an archived contact.
members, markattendance, editevent, deleteevent Still work on archived events.
addevent Rejected if an archived event has the same name, with a hint to unarchive it.
add, addevent Switch the view back to active items, so that the new item is visible.
Event and tag member lists, a contact's event list Archived items are marked (archived).

In the data file, contacts and events store an archived field. A file without this field loads with nothing archived.

Design considerations

Aspect: How archived items are hidden

  • Alternative 1 (current choice): The model combines the archive view with every contact filter.

    • Pros: Every command that filters contacts respects the view without changes. Future filters also respect it.
    • Cons: The filtered list's predicate is no longer exactly the one a command set, so ModelManager must keep the command's predicate separately.

  • Alternative 2: Each command adds !person.isArchived() to its own predicate.

    • Pros: The model stays unchanged.
    • Cons: Easy to forget in a new command, and list archived would have to change every command's behaviour.

Aspect: How archive and unarchive identify a contact

  • Alternative 1 (current choice): By permanent member ID, as edit, delete, and assign do.

    • Pros: Consistent with the other contact commands. A contact can be restored from any view, and a search or filter cannot change which contact an ID refers to.
    • Cons: The user needs to know the ID, which is shown on each contact card.

  • Alternative 2: By index in the displayed list.

    • Pros: Easy to use right after a search.
    • Cons: Restoring a contact would first need list archived, and indexes shift when the list changes.

Aspect: Where archived items are stored

  • Alternative 1 (current choice): In the same lists, with an archived flag.

    • Pros: Names stay unique across active and archived items, events keep referring to archived contacts by name, and unarchiving only flips the flag.
    • Cons: Every list that should hide archived items must filter them out.

  • Alternative 2: In separate archive lists.

    • Pros: The normal lists never contain archived items.
    • Cons: Duplicate checks, event member lookups, and the data file format would all have to handle two lists, and moving an item between lists could break the links between events and contacts.

First-launch tutorial

The tutorial is a step-by-step tour of the main window, shown automatically on the first launch.

Implementation

TutorialWindow is an overlay inside the main window, not a separate window. It holds a fixed list of TutorialStep records, each with a title, a description, where to place the step's card, and a TutorialTarget naming the part of the main window to highlight.

TutorialWindow handles the tour itself, and MainWindow connects it to the rest of the window:

  • Changing steps. When the step changes, TutorialWindow calls the step-change handler set by MainWindow. MainWindow#showTutorialStep switches to the tab that the step needs, finds the node for its TutorialTarget, and passes it to TutorialWindow#highlight. The overlay then shades everything except that node and places the step's card beside it.
  • Blocking the app. While the tutorial is showing, event filters on the overlay and on the main window consume every mouse and key event that is not aimed at the tutorial card. MainWindow#showTutorial also disables the command box. This prevents commands from changing the lists that the tour points at.
  • Keyboard control. TutorialWindow#handleShortcut moves between steps with the Left and Right arrow keys and closes the tour with Esc. Tab cycles focus through the card's buttons without leaving the card.
  • Normal view. MainWindow#showTutorial calls Logic#showActiveItems() first, because the archived view hides the lists and commands that the tour describes.

Showing it once. UserPrefs stores whether the tutorial has been seen. On launch, MainWindow#showTutorialOnFirstLaunch() opens the tutorial only if it has not. Finishing or closing the tour calls Logic#setHasSeenTutorial(true), and the preference is saved with the other user preferences when the app exits. The tutorial can be opened again at any time with the tutorial command, the Tutorial item in the top bar, or F2. TutorialCommand returns a CommandResult that asks MainWindow to show the tutorial.

Design considerations

Aspect: How the tutorial is displayed

  • Alternative 1 (current choice): An overlay inside the main window that highlights the real controls.

    • Pros: Users see the actual tabs, cards, and command box that each step describes, and the overlay can never be separated from the window it explains.
    • Cons: Each step needs a target node, and the overlay must block input to the window underneath.

  • Alternative 2: A separate window with screenshots and text.

    • Pros: Independent of the main window's layout.
    • Cons: Screenshots go out of date whenever the UI changes, and users must map each picture onto the real window.

Keyboard navigation and command history

CoordiMate can be used without a mouse. Besides typing commands, users can move between cards and views with single keys, and recall earlier commands.

Implementation

Interaction modes. MainWindow keeps track of one of two InteractionModes, shown in the label beside the command box:

  • Command mode, the default, in which keys go to the command box.
  • Navigation mode, in which the command box is disabled and single keys act on the selected tab: J and K select the next and previous card, and S switches to the next view.

The state diagram below shows how the user moves between the two modes.

MainWindow#handleKeyboardInput is a key filter on the whole window. In Command mode it only reacts to Esc, which enters Navigation mode. In Navigation mode it handles J, K, and S, and consumes every other unmodified key so that it does nothing. Navigation mode returns to Command mode when I is released, rather than pressed, so that the I does not also appear in the command box. Clicking a card list enters Navigation mode, and clicking the command box or a command row in the sidebar returns to Command mode.

Mode changes are ignored while the tutorial is showing, and while a delete is waiting for confirmation, so that the confirmation stays in the command box.

Moving between cards. CardNavigation moves the selection of a card list by one card and scrolls it into view. With nothing selected, J selects the first card and K the last. At either end of the list, the selection stays where it is, rather than wrapping around. PersonListPanel, EventListPanel, and the tag list all use it, so the three tabs behave the same way.

Command history. CommandBox keeps every submitted command in a list, including commands that failed, so that they can be corrected and run again. The Up and Down keys move through the list. The text being typed before browsing is kept as a draft and restored by pressing Down past the newest command. Submitting a command, or inserting one from the sidebar, resets browsing to the end of the list. Answers to a delete confirmation are not recorded, and Up and Down do nothing while one is pending, so that y is never recalled as a command. The history is kept only for the current session.

Design considerations

Aspect: How single-key navigation coexists with typing

  • Alternative 1 (current choice): A separate Navigation mode, entered with Esc.

    • Pros: Single keys such as J can move between cards without a modifier, as in many keyboard-driven tools, while the same keys still type normally in Command mode.
    • Cons: Users must know which mode they are in, so the current mode is always shown beside the command box.

  • Alternative 2: Shortcuts with a modifier key, such as Ctrl+J, available at all times.

    • Pros: No modes to learn.
    • Cons: Common modifier shortcuts already have meanings in text fields and on different operating systems.

Aspect: Whether command history is saved

  • Alternative 1 (current choice): Keep the history only for the current session.

    • Pros: Nothing extra is written to disk, and the history cannot be corrupted or grow without limit.
    • Cons: The history is lost when the app closes.

  • Alternative 2: Save the history with the user preferences.

    • Pros: Commands can be recalled across sessions.
    • Cons: Adds another file format to maintain, and saves commands that may contain contacts' personal details.

MSS

Non-Functional Requirements

These are acceptance targets, not measured results. Performance tests should use one running CoordiMate instance and a valid data file on writable local storage. Record the OS, Java version, processor, memory, and dataset with the results. Speed and onboarding targets require timed trials with users from the target user profile.

  1. Should run on the mainstream OS platforms with Java 25, targeting the OS and Java configurations used by the project's CI workflow. The packaged JAR should also receive a manual launch check on each target platform before release compatibility is claimed.
  2. Should store and reload a dataset at the maximum typical load. Successfully saved contact details, member IDs, tags, event schedules, assignments, attendance, archive flags, leave dates, and reminder dismissals should survive a normal restart. Performance at this load is assessed using NFR 4. This is a capacity target for the whole local dataset, not an enforced data limit. The app does not partition data by semester.
  3. For users familiar with CoordiMate's keyboard shortcuts, a short sequence of switching views and selecting adjacent cards should take less time on average using shortcuts than using the mouse. Compare repeated trials by the same user from the same starting view and selection, including keyboard mode changes.
  4. Under the typical load, common commands such as add, edit, search, filter, list, addevent, assign, and markattendance should each have a median response time of at most 2 seconds over repeated trials on the recorded test machine. Measure from pressing Enter to visible feedback and completion of the resulting view update, including any save. Exclude application startup and time waiting for user confirmation; measure the prompt and the response after confirmation separately when applicable.
  5. Contact, tag, event, attendance, archive, and reminder features, including built-in Help and the tutorial, should work without an internet connection. Opening the online User Guide requires internet access.
  6. If only the application process terminates during a save while the OS remains running, an existing valid local data file should retain either the previous complete dataset or the new complete dataset. This assumes that the filesystem and Java provider support atomic replacement, as described in Saving data atomically. It covers application data, excluding user preferences, OS crashes, power loss, storage hardware failure, and external file modification.
  7. Application data should be stored in human-readable JSON that users can inspect and back up with ordinary file tools. Manual edits should be made with the app closed and must satisfy the saved-data constraints.
  8. Should be distributed as a single application JAR with no CoordiMate installer, assuming the required Java environment is already installed.
  9. After completing or closing the tutorial, a first-time user from the target user profile should be able to add one contact within 10 minutes without assistance from another person. Supply valid, unique name, phone, email, and role values as task input. Start timing when the command box is ready for input and stop when the saved contact is visible with those details and a success message. Consulting built-in Help, command hints, or the User Guide and correcting commands count towards the limit; installation, launch, and tutorial reading time do not.
  10. Every colour-coded tag should display its name as text so that contact categories can be distinguished without relying on colour.

Glossary

  • Archive: To mark a contact or event as archived, hiding it from the active lists while preserving its details, event assignments, and attendance records.
  • Assigned member: A contact who has been assigned to a particular event. Also referred to as a member of that event.
  • Attendance status: A recorded value of present or absent for an assigned member at an event. A member with no attendance record is shown as unmarked, not automatically absent.
  • CCA (Co-Curricular Activity): A student club or society in a university, such as a band, sports team or interest group.
  • CLI (Command Line Interface): An interface operated by typing text commands. CoordiMate accepts these commands in a command box within its graphical window.
  • Colour-coded tag: A tag whose display colour is assigned by the app based on its name. EXCO, Logistics, Sponsor, and UniversityStaff have distinct built-in colours; other tags share a default colour. Users cannot choose tag or contact colours.
  • Command mode: The keyboard mode for entering commands in the command box.
  • Committee handover: The transfer of responsibilities and information from an outgoing EXCO to the incoming EXCO.
  • Contact: A person whose details are saved in CoordiMate and identified by a member ID.
  • Custom tag: A tag created by the user, to categorise contacts in ways not covered by the default tags.
  • Default tag: A tag that is available without the user creating it: EXCO, Sponsor, UniversityStaff and Logistics.
  • Duplicate contact: A contact with the same name (ignoring case and normalising spaces), normalised phone number, or email address (ignoring case) as another saved contact, including an archived one.
  • Event: A CCA activity recorded in CoordiMate, such as a concert or fair, identified by a name that is unique ignoring case and extra spaces.
  • Event lead: An EXCO member who is in charge of organising a particular event.
  • EXCO (Executive Committee): The group of students elected to lead and run a CCA.
  • External contact: A contact from outside the CCA, such as a sponsor, university staff member, or EXCO member of a collaborating CCA.
  • Future event: An event whose start date/time is later than the current date/time.
  • Internal contact: A contact from within the CCA, such as a member, fellow EXCO member or advisor.
  • JAR file: A single file that packages a Java application so that it can be run without installation.
  • Local data file: The JSON file on the user's computer where CoordiMate saves contacts, tags, events, attendance records, and reminder dismissals. Its default path is data/coordimate.json, relative to the working directory.
  • Mainstream OS: Windows, macOS, or Linux.
  • Member ID: A unique, permanent positive integer assigned to a contact, displayed as ID: <number>, and used in commands across searches, filters, and restarts.
  • Navigation mode: The keyboard mode in which key presses browse cards and switch views.
  • Normalised phone number: A phone number with spaces, hyphens and brackets removed, used to detect duplicates. For example, +65 9123 4567 and +6591234567 are the same.
  • On leave: A contact with a saved leave end date is unavailable through that date, inclusive, using the computer's local date.
  • Organisation: The company or body that a contact belongs to, such as a CCA, sponsor company, or university office.
  • Prefix: The short label before a value in a command that tells CoordiMate which field it belongs to, such as n/ for name or t/ for tag.
  • Reminder: An in-app notice for an upcoming, non-archived event, shown only while CoordiMate is running. Timed starts qualify from 24 hours before the start through the start time; date-only starts qualify on the preceding day and the start date. Reminders refresh at startup, after commands, and once per minute.
  • Role: A contact's responsibility or position in relation to the CCA, such as Logistics Lead or Vice-President.
  • Tag: A short label attached to a contact to categorise it, such as EXCO or Sponsor. A contact can have multiple tags.
  • Tutorial: An in-app introduction to CoordiMate's views, commands, and keyboard navigation.
  • Typical load: A local dataset of up to 250 contacts and 6 events in total, including archived items, with up to 250 assigned members and their attendance records per event.
