Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java.

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The HelpWindow provides an in-app command quick reference. Its read-only, scrollable command table is populated by HelpWindow using the command words defined by the corresponding command classes, while its FXML file controls the resizable layout. The User Guide URL remains available for more detailed instructions. The window's Close button is marked as the JavaFX cancel button, allowing users to dismiss it by selecting the button or pressing Esc without exiting the application.

CommandBox keeps submitted, nonblank commands in a session-only list. The list has no configured cap or eviction; its practical limit is the JVM heap, and it is discarded when the app closes. It records an attempt before execution so commands that fail validation can be recalled for correction. Up and Down move through the list, with the current input saved as a draft and restored after the newest entry. Browsing does not execute a command or modify stored entries. While Logic awaits delete confirmation, arrow-key navigation is paused and the response is not added to history. Inserting a command from the sidebar resets history navigation.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data. The Contacts view displays the filtered contact list beside a details pane, follows a selected contact when an edit replaces that list entry, and clears the selection when the contact leaves the list. The details pane displays all saved contact fields, showing a placeholder for unset optional fields and no tag chips for an empty tag set. It also derives assigned-event rows from the live event list. The Events view resolves each assigned member to contact role, organisation, and tags, and refreshes when contact data changes. Contact and event views keep their details pane above a minimum width, then stack the list above details when the window is narrow. Sidebar command rows insert only the command word into the command box and show its format and an example; rows also support keyboard activation. Selecting a tag shows all saved contacts assigned to it, independent of the current contact filter, and refreshes names, roles, organisations, and tags when contact data changes.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands. The switch command returns a view selection request that MainWindow applies through the same view controls used by the sidebar. LogicManager executes this navigation command without reading or saving contact data.
  • depends on some classes in the Model component because it displays Person objects from the model.

API : Logic.java

Note: This diagram and the architecture sequence diagram above are simplified to show the general flow of a command. In the actual implementation, delete first asks the user for confirmation, and commands that change data are executed on a copy of the model and saved before the change is applied. Both are described in Saving data atomically.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a CoordiMateParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Here are the other classes in Logic (omitted from the class diagram above) that are used for parsing a user command:

How the parsing works:

  • When called upon to parse a user command, the CoordiMateParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The CoordiMateParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Command error messages follow these conventions:

  • Use sentence case and full stops for explanations, without an Error! prefix or exclamation marks.
  • For malformed command syntax, use ParserUtil.createInvalidFormatException(Command.MESSAGE_USAGE). Usage text has a command description, Parameters:, and Example: on separate lines.
  • Every command error includes the relevant command's usage once. CoordiMateParser appends it to parse errors; LogicManager appends it to execution and storage errors. Messages.withUsage avoids duplicating usage.
  • For unknown or repeated parameters, name the offending prefix: Unknown parameter: x/. or Parameter evn/ may only be specified once.
  • For invalid field values, explain the constraint and provide an Example: using the failing parameter's prefix.
  • Distinguish missing parameters, which show command-format guidance, from supplied but empty values, which use <Field> must not be empty. Example: <prefix><value>. Optional contact fields can still be cleared intentionally.
  • Storage-loading errors use Saved data could not be loaded. Check the local data file. for every data type.
  • For execution errors, explain what failed and how to correct it. Reuse the templates in Messages for missing contacts, events, and tags, and for unmatched or ambiguous contact identifiers.
  • Add No changes were made. when an attempted change is rejected without modifying the saved data.

Model component

API : Model.java

The Model component,

  • stores CoordiMate data, including all Person objects (which are contained in a UniquePersonList object).
  • stores all Event objects. Each Event records its assigned members as an ordered list of contact Names. CoordiMate keeps these lists in sync with the contacts: deleting a contact removes their name from every event, and renaming a contact updates it.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in CoordiMate, and each Person references tags from that list. This lets CoordiMate maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both CoordiMate data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonCoordiMateStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Previously saved digit-only phone numbers with at least three digits remain valid model data, so older JSON files can still load. The command parser applies the current 7–15-digit rule whenever a user supplies a phone number for add or edit; editing another field does not require replacing a legacy phone number.

Common classes

Classes used by multiple components are in the coordimate.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Saving data atomically

A command that changes data either takes effect in full, both in the app and in the data file, or not at all. This keeps the displayed data and the saved data identical even when the data file cannot be read or written, and meets the requirement that saved data is not lost if the app terminates unexpectedly.

Implementation

Two mechanisms work together.

1. Commands run on a copy of the model. LogicManager#execute passes every command that changes data to LogicManager#executeAtomicCommand. These are AddCommand, EditCommand, DeleteCommand, ClearCommand, AddEventCommand, EditEventCommand, DeleteEventCommand, AssignCommand, UnassignCommand, MarkAttendanceCommand, and the tag commands that extend MutatingTagCommand.

executeAtomicCommand does the following:

  1. It calls Storage#readCoordiMate() to check that the existing data file can still be loaded. If it cannot, the command is rejected with a load error and the file is left untouched, so that the user can repair it. A missing data file is not an error.
  2. It creates a second ModelManager, the candidate, from a copy of the live model's data. The candidate's filtered contact list is set to show the same contacts as the live displayed list, so that a contact index typed by the user refers to the same contact in both models.
  3. It executes the command on the candidate. If the command fails, the candidate is discarded.
  4. It saves the candidate's data with Storage#saveCoordiMate. If saving fails, the command is rejected with a save error such as Event could not be saved. No changes were made. and the candidate is discarded.
  5. Only then does it call Model#setCoordiMate to replace the live model's data with the candidate's data, which updates the UI.

The live model is not touched until step 5, so a failure at any earlier step leaves the app exactly as it was.

After committing, LogicManager adjusts the displayed contact list where needed: add and edit show all contacts again so that the changed contact is visible, and renaming an event whose members are being shown keeps that view on the renamed event (see Keeping events in sync with contacts).

2. The data file is replaced in one step. JsonCoordiMateStorage#saveCoordiMate writes the new data to a temporary file named coordimate-*.tmp in the same folder as the data file, then moves it over the data file using StandardCopyOption.ATOMIC_MOVE. The data file therefore always holds either the complete old data or the complete new data. The temporary file is deleted if anything fails.

Deleting a contact adds a confirmation step. For a delete command, LogicManager checks that the data file can be loaded, resolves the contact, stores it in its pendingDelete field, and returns a confirmation prompt. The next input is treated as the answer, not as a command: y or Y runs the deletion through executeAtomicCommand, and any other input cancels it.

Commands that do not change data, such as list, search, filter, members, and listtags, are executed directly on the live model. As in AddressBook-Level3, LogicManager still saves the model afterwards. This has two consequences that developers should be aware of:

  • If the data file is invalid, such a command replaces it with the data currently in the app.
  • If the data file cannot be written, such a command reports a save error even though it changed no data.

switch is a UI navigation command and an exception to this save path. SwitchCommandParser accepts only contacts, events, or tags after the command word. LogicManager returns its CommandResult without reading or saving the data file; MainWindow selects the requested tab and updates the sidebar through its existing tab selection listener. Invalid view names are rejected before the UI changes.

Design considerations

Aspect: How a command is prevented from taking effect when saving fails

  • Alternative 1 (current choice): Execute the command on a copy of the model, save the copy, then replace the live model's data.

    • Pros: Works for every command without command-specific code. The UI never shows a change that was not saved.
    • Cons: Copies all data for each command, which is acceptable for the expected 250 contacts. Each new command that changes data must be added to the list in LogicManager#execute.

  • Alternative 2: Execute the command on the live model, and restore a snapshot if saving fails.

    • Pros: No copy is needed when saving succeeds.
    • Cons: The UI observes the model, so it briefly shows a change that is then reverted.

  • Alternative 3: Have each command undo its own change if saving fails.

    • Pros: Uses the least memory.
    • Cons: Every command needs correct undo logic, which is easy to get wrong.

Event attendance

Attendance records whether each member of an event was present or absent.

Implementation

An Event is immutable. It stores:

  • its members as a List<Name> of contact names, in the order they were assigned.
  • its attendance as a Map<Name, AttendanceStatus>, where AttendanceStatus is an enumeration of PRESENT and ABSENT. A member with no entry in the map has not been marked.

The Event constructor rejects an attendance record that contains a name which is not a member, so attendance can never exist for someone who is not assigned to the event.

The markattendance command works as follows:

  1. MarkAttendanceCommandParser checks that evn/, mem/, and att/ each appear exactly once, converts the status with AttendanceStatus#fromString, and validates the member name with ParserUtil#parseName.
  2. MarkAttendanceCommand#execute finds the event and then the member, both ignoring case. It uses the member's name as stored in the event, so that feedback and the attendance record use the saved capitalisation.
  3. If the member already has the requested status, the command reports that no changes were made.
  4. Otherwise it calls Event#withAttendance, which returns a copy of the event with the member's status set, and replaces the event with Model#setEvent.

The command changes data, so it runs through executeAtomicCommand as described above.

Other commands keep the attendance record consistent with the members:

Change Effect on attendance
assign adds members Existing attendance is kept. New members are not marked.
unassign removes members The removed members' attendance is removed.
editevent renames or reschedules the event Attendance is kept.
edit renames a contact The contact's attendance moves to the new name in every event.
delete deletes a contact The contact's attendance is removed from every event.

In the data file, JsonAdaptedEvent stores attendance as an attendance object that maps each member's name to "present" or "absent". A file with no attendance field loads with no attendance recorded, so files saved by earlier versions still load. A file is rejected as invalid if a status is neither value or if a name in attendance is not in the event's members.

EventListPanel shows Present, Absent, or Not marked beside each member of the selected event, and the number of members with each status.

Design considerations

Aspect: Where attendance is stored

  • Alternative 1 (current choice): Each Event stores a map from member name to status.

    • Pros: An event and its attendance are saved, copied, and replaced as one unit, so they cannot disagree. Removing a member and their attendance is a single change.
    • Cons: A contact's attendance across events can only be found by looking through every event.

  • Alternative 2: Store attendance records in a separate list, each referring to an event and a contact.

    • Pros: Makes it easy to query one contact's attendance across all events.
    • Cons: Every change to an event or contact must also update the separate list, or records are left behind.

Aspect: How "not marked" is represented

  • Alternative 1 (current choice): A member with no entry in the map is not marked.

    • Pros: Newly assigned members need no extra data, and older data files load without conversion.
    • Cons: Code that counts statuses must derive the not-marked count from the members.

  • Alternative 2: Add a third NOT_MARKED status and give every member an entry.

    • Pros: Every member has an explicit status.
    • Cons: Every command that adds a member must also add an entry, and older data files would need converting.

Filtering contacts

The filter command lists the contacts that match every given FIELD/VALUE pair, where the field is tag, event, or organisation.

Implementation

Filtering is split into parsing, which does not need saved data, and resolving, which does.

Parsing. FilterCommandParser turns the arguments into a list of FilterCriterion records, each holding a FilterField and the value as typed.

  1. It finds every FIELD/ token, which is a run of letters followed by / at the start of the arguments or after a space. A token is ignored if an odd number of quotation marks comes before it, since it is then inside a quoted value.
  2. The value of each field is the text up to the next token. Surrounding quotation marks are removed.
  3. The field name is matched to a FilterField, ignoring case.

An unclosed quotation mark is rejected only when a FIELD/ token follows it, because it is then unclear where the value ends. With no token after it, the quotation mark is kept as part of the value, since saved names may contain one. For example, filter event/"Cali matches an event named "Cali.

Resolving. FilterCommand#execute turns each criterion into a Predicate<Person> using the model:

Field The value must match, ignoring case A contact matches if
tag a tag in Model#getTagList() it has that tag
event the name of a saved event it is a member of that event
organisation the organisation of at least one saved contact its organisation is that value

If a value matches nothing, the command throws a CommandException with No matching value found. before the displayed list is changed. This tells the user about a mistyped value instead of showing an empty list. Otherwise the predicates are combined with Predicate#and and passed to Model#updateFilteredPersonList.

filter does not change data, so it is executed directly on the live model.

Note: The event predicate holds the Event found when the command was executed. Since an Event is immutable, the filtered list does not follow later changes to that event's members until filter is run again. The members command differs: it uses EventMembersPredicate, which looks the event up each time it is tested.

To add a filter field, add a constant to FilterField, add a case to FilterCommand#resolvePredicate, and update FilterCommandParser.MESSAGE_INVALID_FIELD.

The search command is implemented separately. SearchCommand uses ContactMatchesKeywordPredicate, which tests whether a contact's name, phone, email, address, or organisation contains the keyword, ignoring case.

Design considerations

Aspect: Syntax of a filter

  • Alternative 1 (current choice): Full field names, as in filter tag/EXCO event/Final Concert.

    • Pros: The fields are self-explanatory, and a field is added by extending one enumeration.
    • Cons: Differs from the short prefixes of other commands, such as t/.

  • Alternative 2: Reuse the existing prefixes, as in filter t/EXCO evn/Final Concert.

    • Pros: Consistent with other commands.
    • Cons: Some prefixes would mean different things in different commands, and organisation would need o/, which is easy to confuse with other single-letter prefixes.

Aspect: What happens when a value does not exist

  • Alternative 1 (current choice): Reject the command with No matching value found.

    • Pros: Distinguishes a mistyped value from a valid value that no contact has.
    • Cons: The command must look the value up in the model before filtering.

  • Alternative 2: Show an empty list.

    • Pros: Simpler to implement.
    • Cons: The user cannot tell whether the value was mistyped.

Keeping events in sync with contacts

An event refers to its members by contact Name, not by Person object. Contacts are replaced with new Person objects whenever they are edited, so a name is the stable way to refer to one. In exchange, the app must keep the names in events consistent with the saved contacts.

Implementation

Renaming and deleting contacts. CoordiMate updates events whenever a contact changes:

  • CoordiMate#setPerson checks whether the contact's name has changed. If so, every event that lists the old name is replaced with a copy that lists the new name in the same position and carries the contact's attendance over.
  • CoordiMate#removePerson replaces every event that lists the contact with a copy that has neither the name nor its attendance.

Both use CoordiMate#getEventsWithReplacedMember, which builds all the updated events before anything is changed. As a safeguard, if an event already has a member with the new name, it throws MemberNameConflictException and no data is changed. EditCommand reports this as Cannot rename this contact because an event already has a member with that name. No changes were made.

Loading data. JsonSerializableCoordiMate#toModelType rejects a data file in which an event lists a member who is not a saved contact, with Event members must refer to existing contacts.

Showing an event's members. MembersCommand filters the contact list with EventMembersPredicate. The predicate holds the event's name and the model's live event list, and looks the event up each time it is tested. The displayed members therefore follow later changes:

  • After unassign, the removed member no longer matches and disappears from the list.
  • After deleteevent, no event has that name, so the list becomes empty.
  • After editevent renames the event, the old name would match nothing, so LogicManager#keepMembersViewAfterRename replaces the predicate with one for the new name.

A filtered list re-tests its predicate only when the contact list changes. For this reason CoordiMate#resetData replaces the events before the contacts: when the contacts are replaced and the predicate is tested again, it already sees the new events.

Design considerations

Aspect: How an event refers to its members

  • Alternative 1 (current choice): By contact name.

    • Pros: Readable in the data file, where members is a list of names. Names are already unique among contacts.
    • Cons: Renaming or deleting a contact must update every event, as described above.

  • Alternative 2: By a reference to the Person object.

    • Pros: No lookup is needed to get a member's details.
    • Cons: Person is immutable and is replaced on every edit, so every event would need updating on any edit, not only on a rename.

  • Alternative 3: By a generated contact ID.

    • Pros: Renaming a contact would not affect events.
    • Cons: Needs a new ID field and a change to the data file format, and makes the data file harder to edit by hand.

Appendix: Requirements

Product scope

Target user profile:

  • is a university CCA EXCO member managing information for one organisation
  • needs to manage the organisation's contacts, events, and attendance records
  • needs to preserve useful information for future committee members
  • prefers desktop apps over other types of applications
  • can type fast
  • prefers typing to mouse interactions
  • is reasonably comfortable using CLI apps

Value proposition: CoordiMate helps university CCA EXCO members organise contacts, coordinate events, track attendance, and preserve important information to support smooth committee handovers.

Use cases

(For all use cases below, the System is the Coordimate and the Actor is the user, unless specified otherwise)

Use case: Add a contact

System: CoordiMate

Actor: University CCA EXCO member

Preconditions: CoordiMate is running.

Main success scenario (MSS)

  1. EXCO member requests to add a contact, providing the contact's name, phone number, email address, role, and any applicable optional details.

  2. CoordiMate validates the supplied fields, registers any new custom tags, saves the contact, and confirms that the contact was saved.

    Use case ends.

Extensions

  • 1a. A required detail is missing, empty, repeated, or invalid, or the EXCO member provides an unknown field.

    • 1a1. CoordiMate informs the EXCO member of the error.

    • 1a2. EXCO member corrects the contact details.

      Steps 1a1-1a2 are repeated until the contact details are valid.
      Use case resumes from step 2.

  • 1b. A contact with the same name (ignoring case and surrounding spaces), normalised phone number, or email address already exists.

    • 1b1. CoordiMate informs the EXCO member that the contact already exists and makes no changes.

      Use case ends.

  • 2a. CoordiMate cannot write to the local data file.

    • 2a1. CoordiMate informs the EXCO member that the contact could not be saved and makes no changes.

      Use case ends.

  • 2b. CoordiMate cannot load the local data file because it is invalid or corrupted.

    • 2b1. CoordiMate informs the EXCO member that the contact data could not be loaded and makes no changes.

      Use case ends.

Use case: Search contacts

System: CoordiMate

Actor: Event lead

Preconditions: CoordiMate has been launched and contains at least one contact.

MSS

  1. Event lead requests to search contacts using one or more names, tags, or roles.

  2. CoordiMate displays the contacts that match the given criteria.

    Use case ends.

Extensions

  • 1a. Event lead provides no search criteria.

    • 1a1. CoordiMate displays an error message.

      Use case ends.

  • 1b. One or more search criteria are invalid.

    • 1b1. CoordiMate displays an error message identifying the invalid criteria.

      Use case ends.

  • 2a. No contact matches the given criteria.

    • 2a1. CoordiMate informs the event lead that no matching contacts were found.

      Use case ends.

Use case: Delete a contact

System: CoordiMate

Actor: University CCA EXCO member

Preconditions: CoordiMate is running and at least one contact has been saved.

Main success scenario (MSS)

  1. EXCO member requests to delete a contact, identifying the contact by its displayed index, exact name, phone number, or email address.

  2. CoordiMate displays the matching contact and requests confirmation.

  3. EXCO member confirms the deletion.

  4. Coordimate model without the selected contact, their assignments in any event roster, or their associated attendance records, then updates the live model and confirms the deletion. Events and other contacts remain unchanged.

    Use case ends.

Extensions

  • 1a. The EXCO member provides no identifier, more than one identifier, an unknown field, or an invalid index.

    • 1a1. CoordiMate informs the EXCO member of the error.

    • 1a2. EXCO member provides one valid identifier.

      Use case resumes from step 2.

  • 1b. No contact matches the provided identifier.

    • 1b1. CoordiMate informs the EXCO member that no matching contact was found.

      Use case ends.

  • 1c. More than one contact matches the provided name.

    • 1c2. EXCO member provides one of the requested identifiers.

      Use case resumes from step 2.

  • 3a. EXCO member declines the deletion.

    • 3a1. CoordiMate leaves the contact unchanged. Only y or Y confirms; any other input cancels and is consumed.

      Use case ends.

Use case: Create an event

Preconditions: CoordiMate is running.

MSS

  1. The Exco member creates an event by entering its name, start date/time, and end date/time using the addevent command.

  2. CoordiMate validates the details and creates the event.

  3. CoordiMate displays a confirmation with the event name and its start and end times.

    Use case ends.

    • 2a1. CoordiMate displays the relevant error and does not create the event.

Non-Functional Requirements

  1. Should work on any mainstream OS (Windows, macOS, Linux) as long as it has Java 25 or above installed.
  2. Should be able to hold up to 250 contacts and 6 events per semester without a noticeable sluggishness in performance for typical usage.
  3. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.
  4. Should respond to any user command within 2 seconds under typical load (up to 250 contacts, 6 events).
  5. Should not require an internet connection to operate, since all contact, event, and attendance data is stored and managed locally.
  6. Should not lose previously saved data if the application terminates unexpectedly (e.g. crash, power loss) mid-operation.
  7. Data should be stored in a human-editable, non-proprietary file format (not a DBMS), so users can back up, inspect, or migrate their data manually.
  8. Should be shipped as a single JAR file that does not require a separate installer.
  9. A first-time user with no prior experience should be able to complete the in-app tutorial and add their first contact within 10 minutes.
  10. The colour-coding feature should not be the sole means of distinguishing contact categories, so the app remains usable by colour-blind users (e.g. tags are also shown as text).

Glossary

  • Archive: To move a contact or event out of the active list without permanently deleting it, so that it can still be retrieved later.
  • Assigned member: A contact who has been assigned to a particular event. Also referred to as a member of that event.
  • Attendance status: Whether an assigned member was present or absent at an event.
  • CCA (Co-Curricular Activity): A student club or society in a university, such as a band, sports team or interest group.
  • CLI (Command Line Interface): A way of using the app by typing text commands, as opposed to clicking buttons in a graphical interface.
  • Colour-code: To assign a colour to a contact so that contacts of the same role or group can be recognised visually.
  • Committee handover: The transfer of responsibilities and information from an outgoing EXCO to the incoming EXCO.
  • Contact: A person saved in CoordiMate, with details such as name, phone number, email address and role.
  • Custom tag: A tag created by the user, to categorise contacts in ways not covered by the default tags.
  • Default tag: A tag that is available without the user creating it: EXCO, Sponsor, UniversityStaff and Logistics.
  • Displayed index: The number shown beside a contact in the currently displayed list, used to identify that contact in commands.
  • Duplicate contact: A contact with the same name (ignoring case and surrounding spaces), normalised phone number, or email address as another saved contact.
  • Event: An activity organised by the CCA, such as a concert or fair, with a unique name, a start date/time and an end date/time.
  • Event lead: An EXCO member who is in charge of organising a particular event.
  • EXCO (Executive Committee): The group of students elected to lead and run a CCA.
  • External contact: A contact from outside the CCA, such as a sponsor, university staff member, or EXCO member of a collaborating CCA.
  • Future event: An event whose start date/time is later than the current date/time.
  • Internal contact: A contact from within the CCA, such as a member, fellow EXCO member or advisor.
  • JAR file: A single file that packages a Java application so that it can be run without installation.
  • Local data file: The file on the user's computer where CoordiMate automatically saves all contacts, events and attendance records.
  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Normalised phone number: A phone number with spaces, hyphens and brackets removed, used to detect duplicates. For example, +65 9123 4567 and +6591234567 are the same.
  • On leave: A temporary status marking a contact as unavailable until a specified date, after which it is cleared automatically.
  • Organisation: The external company or body that a contact belongs to, such as a sponsor company or university office.
  • Prefix: The short label before a value in a command that tells CoordiMate which field it belongs to, such as n/ for name or t/ for tag.
  • Role: A contact's responsibility or position in relation to the CCA, such as Logistics Lead or Vice-President.
  • Tag: A short label attached to a contact to categorise it, such as EXCO or Sponsor. A contact can have multiple tags.
  • Telegram handle: A user's username on the Telegram messaging app, such as @aishatan.
  • Tutorial: An in-app guide that introduces a first-time user to CoordiMate's key features.
  • Typical usage: Using CoordiMate with up to 250 contacts and 6 events, as described in the NFRs.

      Expected: The corrupted file is replaced with the app's empty data. Restore the copy of the file to get the original data back.

  3. Dealing with an event member who is not a contact

    1. Prerequisites: The app is closed and data/coordimate.json contains an event with at least one member. Keep a copy of the file.

    2. Test case: In the data file, change one name in an event's members list to a name that no contact has, save, then launch the app.
      Expected: The file is treated as invalid, so the app starts with no contacts and no events. Restore the copy of the file afterwards.

  4. Dealing with a failed save

    1. Prerequisites: The app is running and data/coordimate.json exists. Make the data impossible to save: on Windows, open the properties of data/coordimate.json and tick Read-only; on macOS or Linux, run chmod a-w data in the folder containing the JAR file.

    2. Test case: addevent evn/Test st/01-01-2027 et/01-01-2027
      Expected: No event is added and the Events tab is unchanged. The status message shows Event could not be saved. No changes were made.

    3. Test case: add n/Test Person p/91234567 e/testperson@example.com r/Member
      Expected: No contact is added. The status message shows Contact could not be saved. No changes were made.

    4. Test case: Undo the change made in the prerequisites (untick Read-only, or run chmod u+w data), then repeat the addevent command.
      Expected: The event is added.
